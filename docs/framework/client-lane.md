# client-core.js — ONE AUTHORITY, OR NONE (2026-08-21, inert)

🔑 **A FRAME ASKS THE PROCESS THAT KNOWS.** Sixteen short-lived processes had no common ground but the disk, so a FILE was made to carry a conversation between peers — lock, atomic publish, lock-less fallback, bounded retries, three flaky. Here the frame asks over a kernel object and the kernel serialises, as it always has. Same protocol as the HTTP lane, so a harness without an `http` handler (Codex) becomes a client too, and loses the files with it.
🛑 **THE FALLBACK WRITES NOTHING, AND THAT IS THE WHOLE DESIGN.** A local fallback that wrote to the state files while a daemon holds its own memory makes TWO memories: a `once` delivered by one is re-delivered by the other, for ever, with nothing to see. So no daemon ⇒ deliver `injectLockless` (everything except `once`, proved sufficient by TLC) and record nothing. **One authority, or none.**
🛑 **THE EMPTY STATE HERE IS A FACT, NOT A GUESS — and the opposite rule holds one lane over.** On the spawn lane the lock-less path MUST read the file (production bug 2026-08-07: deciding on `{}` re-emitted a delivered `once`). Here there is no file and no daemon, so "nothing was recorded" is the truth of the system. The two situations look alike and are opposites: never copy one rule onto the other.
⚠️ **NO TIMER, AND NONE MAY BE ADDED.** A missing pipe answers `ENOENT`, a dead socket `ECONNREFUSED`, immediately. If a cell of `client-core.test.js` ever needs a delay to pass, this lane has stopped asking the kernel and started guessing.
⚠️ **THE ABSENCE IS NOT SILENT**: the fallback goes through `pretool-core`, which counts what it withheld and announces it — one universal rule instead of a daemon-specific probe (`gate.md`). No liveness probe exists anywhere in this lane, by decision.
⚠️ **ANTI-VACUITY IS THE POINT OF THE DISK CELL**: asserting "the inert store wrote nothing" passes trivially, since it writes NOWHERE — including from a store aiming at the real state directory. The CONTROL (same folder, same call, the REAL store, a file must appear) is what gives the emptiness meaning. Seen red by making `saveState` write.

## ALL THE CONSUMERS, OR NONE — the partial migration, MEASURED then rolled back (2026-08-21)

🔴 **THE INJECTION STATE HAS FOUR CONSUMERS, AND WIRING ONE OF THEM IS A SPLIT BRAIN**: `doc-inject` (the gate — `doc-seen-`, memoised `plan-`) · `session-inject` (SHARES the `remainder-` queue with the gate) · `turn-count` (the counter `driftUnit: "turn"` reads) · `ctxroute-reset` (PreCompact — erases everything). **MEASURED** with the gate on the daemon and the three others on disk: inject → `once` consumed → run the REAL PreCompact hook → ask again ⇒ the daemon answers **2 bytes**. After a compaction, skills and `once` documents never come back — no error, no badge, no red.
🛑 **A SHARED STATE IS MIGRATED FOR ALL ITS CONSUMERS OR FOR NONE** (expand/contract). A partial migration is SILENT, and silent is the only failure this project refuses outright.
🛑 **THE LANE IS AN ARGUMENT** — `--client [address]` in the wiring, `client.clientLane(process.argv)` in the shell, `LANE_FLAG` declared ONCE so four shells cannot drift apart. Absent ⇒ today's behaviour BYTE FOR BYTE, differentials green untouched; rollback = delete the word. NEVER an environment variable: env vars are INHERITED, and one leak makes a spawned hook read an EMPTY memory — every `once` re-delivered, no error anywhere.
🛑 **FOUR ROUTES, ONE HANDLER, ONE `store`**: `/pretool` (the gate, unchanged — and the default for any unknown path, which is what keeps old clients identical) · `/purge` `{keys:[…]}` → `{purged:N}` · `/turn` `{prefix,scope}` → `{turns:N}` · `/emit` `{frais,budgetMax,nbFrames,indice,scopeId}` → `{plan}`. Two stores would be the "two memories" defect, reintroduced from inside the daemon.
🛑 **EVERY ROUTE IS SYNCHRONOUS, AND THAT IS WHAT MAKES IT ATOMIC** — one connection at a time onto a single-threaded loop. NEVER split a read-modify-write into a `load` request and a `save` request: two round trips are two moments, i.e. a file made to carry a conversation between peers, rebuilt over a socket.
🛑 **THE PURGE IS AN ORDER RECEIVED, never a deduction here that a session is over**, and `memory-store-pure.purge()` (which already clears BOTH key classes) is REUSED, never rewritten. The KEYS come from the shell: the five prefixes have ONE owner — the loop `store-purge-gate` reads.
🔴 **AN EMPTY KEY IS REFUSED BY `/purge`**: every key starts with the empty string, so one malformed payload would erase the WHOLE fleet's memory in a single call.
⚠️ **THE DISK PURGE STAYS ON BOTH LANES — the ONE operation where that is safe.** A purge only DESTROYS and is idempotent, so it can never record a delivery and cannot make two memories; every other operation is daemon-ONLY on the client lane.
⚠️ **`Infinity` CANNOT TRAVEL IN JSON** (`JSON.stringify(Infinity)` is `null`) ⇒ on `/emit` a positive finite number is the budget and `null` MEANS "this harness bounds nothing". Stated on both sides, guessed on neither.
⚠️ **THE INCREMENT RULE LIVES IN `turn-core.js`**, shared by the daemon and the spawned shell: a rule about the shape of a store, read in two places, diverges (paid twice — ㊱, ㊳).
⚠️ **A `--client` TOKEN STARTING WITH `-` IS THE NEXT FLAG, NEVER AN ADDRESS.** Absent ⇒ `endpoint()`, this repository's one rendezvous; present ⇒ a cell drives a daemon OF ITS OWN instead of the machine's.
⚠️ **THE CELL SPAWNS THE REAL SHELL** (`daemon-purge.test.js`): deliver → silent → REAL PreCompact process → it must COME BACK. The silence in the middle IS the anti-vacuity — without it the cell passes on a daemon holding no state at all. **A green on a twin is not a green on the thing.**

## Publishing a new version — MEASURED 2026-08-21, and the obvious plan is REFUTED

🔴 **WINDOWS HAS NO DOCUMENTED ATOMIC DIRECTORY SWAP. Do not design one.** `MoveFileExW`: *"If lpNewFileName names an existing directory, an error is reported"* (learn.microsoft.com, `MOVEFILE_REPLACE_EXISTING` table, page updated 2025-07-01), and [MS-FSA] `FileRenameInformation` makes it normative: *"The operation MUST be failed with STATUS_ACCESS_DENIED … If TargetLink.File.FileType is DirectoryFile"* (updated 2025-09-09). A junction and a directory symlink ARE directories ⇒ swapping a release by renaming a link over another is not "non-atomic", it is **refused**.
⚠️ **AND THE WORD `atomic` APPEARS ON NONE OF THEM** — `MoveFileEx`, `ReplaceFile`, `FILE_RENAME_INFO` promise nothing. The only mechanism Microsoft ever presented as atomic is TxF, and it *"is considering deprecating TxF APIs in a future version of Windows"* (updated 2025-03-12). ⇒ **Never claim an atomicity Windows does not document.**
⚠️ **RENAMING A DIRECTORY THAT HAS OPEN FILES FAILS**, loudly: [MS-FSA] *"If Open.File contains open files … the operation MUST be failed with STATUS_ACCESS_DENIED"*. Under a fleet of agents spawning through the path, that is the normal case, not the edge case.
✅ **WHAT IS DOCUMENTED AND USABLE**: `FSCTL_SET_REPARSE_POINT` *"allows the calling program to set a new reparse point, or to modify an existing one"*, with `CreateFile` + `FILE_FLAG_OPEN_REPARSE_POINT` to hold the LINK rather than its target (both updated 2025-03-12). It re-targets **in place**: the directory is never deleted, so the state "the path does not exist" is not produced BY CONSTRUCTION — which is weaker than a promise of atomicity and different in nature. Say it that way, never as a guarantee.
📐 **POSIX, for contrast**: `rename()` — *"a directory entry named new shall remain visible to other threads throughout the renaming operation"* (IEEE Std 1003.1-2024). Exactly the guarantee Windows gives nowhere.
⚠️ **DIVERGENCE BETWEEN TWO DATED SOURCES, RECORDED NOT MERGED**: the `FILE_RENAME_INFO` API page (2026-05-15) says flatly *"the target file will be replaced"* with no directory caveat; [MS-FSA] (2025-09-09) refuses it normatively. The protocol spec is the algorithmic authority; the API page is incomplete.

## Switching over — ONE LINE PER HARNESS, never a new file

🛑 **A SECOND SHELL PER HARNESS WAS WRITTEN ON 2026-08-21 AND DELETED THE SAME HOUR — the maintainer caught it, and the reasoning is worth more than the code.** Adding a second client shell beside each existing one (Claude, then its Codex twin) multiplies LANES × HARNESSES: every future harness would owe two shells instead of one, and the count would grow again at the next lane. That is the engine moving because a need appeared — precisely what §0bis forbids. **If it moves, we shipped a tool, not a language.**
✅ **THE ONLY DIFFERENCE BETWEEN THE TWO LANES IS WHO OWNS THE STATE, and this repository already made that an ARGUMENT.** So the switch-over is, in each EXISTING shell, replacing `run(data, emit, opts)` with `client.run(data, { output, emit }, opts)` — the dialect, the lifecycle and the file itself are untouched. Rolling back is the same line, the other way.
⚠️ **WHAT A NEW HARNESS OWES, IN FULL**: one shell (its stdin/stdout dialect, 15–50 lines) — the SAME one for both lanes. `HARNESS-CONTRACT.md` and `doctor --harness <real payload>` are an EXAM, not a generator: they answer *"does this harness expose what the engine requires?"* with `supported` / `degraded` (each point named) / `incompatible`. No contract can remove the shell, because no contract can guess another product's JSON shape.
⚠️ **THE ONE REAL CONSTRAINT, STATED RATHER THAN HIDDEN**: asking the daemon is a socket round trip, so the answer arrives on a LATER TICK, while `pretool-core.run` answers synchronously. A shell on this lane therefore must NOT `process.exit(0)` after calling — `emit` exits when there is something to say, and the loop empties by itself otherwise. That asymmetry is the reason the two lanes looked like they needed two shells; they do not.
