# invocation-snapshot-pure.js — the arrival order survives the daemon's death

🔴 **BORN OF A RE-INJECTION MEASURED IN PRODUCTION 2026-09-19, ON THE OPERATOR'S OWN CONVERSATIONS.** This daemon exits BY DESIGN at every code delivery (`process.exit(90)`), and the accepted criterion is that a restart is invisible to the agent. **It was not, for an invocation IN FLIGHT** — and the reason is that TWO states were conflated: `doc-seen-` says WHICH documents were delivered and lives on disk, so it survives; the three invocation tables say WHICH CHUNK the k-th arriving frame serves and live in RAM, so they die. A restart therefore keeps every document marked delivered AND resets the arrival counter, so the frames landing afterwards are counted as the FIRST and re-serve chunk 1. **The document is not re-decided; the CHUNK is re-served**, and the agent sees its skill arrive a second time mid-session.
🛑 **THE FAULT THAT HID IT IS THE ONE TO REMEMBER**: an agent photographed `doc-seen-` before and after a restart, found it intact, and declared "zero document re-delivered". TRUE, and beside the question. **Proving the durable half and concluding on the whole state** is this repository's oldest error shape — committed here by the agent that had repaired those very tables the same morning.
🛑 **THE COST IS PAID AT DEATH, NEVER IN SERVICE, and that is why this is NOT a development-mode feature.** Writing these tables per frame would be 32 disk writes per action against a declared SSD-wear budget, and it was refused for that; one write while the process is exiting costs a SERVING daemon exactly nothing. A guard against a PRODUCTION defect that only runs in development protects the machine where the defect does not matter.
⚠️ **WHICH DEATHS IT COVERS**: `process.exit(90)` fires `'exit'`, so the stale-code restart — every code delivery, the frequent one — is covered. `SIGKILL` and a power loss are NOT, and that residual is BOUNDED: it degrades to exactly today's behaviour, on a death that is rare instead of routine.
🔴 **THE THREE TABLES DO NOT HOLD THE SAME SHAPE, AND ASSUMING THEY DID MADE THIS MODULE REFUSE ITS OWN SNAPSHOT.** `frame-sequencer-pure` stores a plain NUMBER (the arrival count); `delivery-notice-pure` and `carryover-pure` store records. A value check written for "an object" rejected every real snapshot — **a fix that ships INERT**, and five cells built on a FABRICATED fixture passed on it. Only the cell that drives the REAL sequencer saw it. ⇒ **SI you add a table here, you MUST copy its value shape from the module that owns it**, and the cell that proves it MUST call that module.
🛑 **FAIL-OPEN TO EMPTY, ALWAYS, AND NEVER HALFWAY**: unknown version, malformed entry, anything unparsed ⇒ THREE empty tables, never two good ones and a broken third — the sequencer and the carryover disagreeing about one invocation is a state nobody can reason about. Empty is exactly what today already costs.
⚠️ **`adopt` FILLS THE LIVE MAPS IN PLACE, NEVER REPLACES THEM.** `main` builds the three tables once and hands them to EVERY `createServer` of the port lane — that sharing is what closed the 2026-09-19 duplication where one table per socket re-served chunks 1..8 four times each. Replacing a table here would hand the servers a map nobody writes to and rebuild that defect from the other end.
⚠️ **TRUNCATION KEEPS THE TAIL**: the tables are LRU-ordered by insertion, so the newest entries are the invocations still in flight — precisely what a restart must not lose. Keeping the head would faithfully preserve what no longer matters.
⚠️ **NO tmp+rename, DELIBERATELY**: a truncated file fails `JSON.parse`, the decode is fail-open, and the next clean exit rewrites it whole. Atomicity protects a TRUTH; this is a cache of arrival counters whose worst loss is what we already accept.
