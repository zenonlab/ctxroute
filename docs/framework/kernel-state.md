# memory-store · kernel-endpoint · state-client — THE KERNEL SERIALISES, THE DISK ONLY SAVES (2026-08-20)

🔑 **THE RULE, AND EVERY LINE BELOW IS A CONSEQUENCE OF IT: the OS for what is ALIVE, the disk ONLY to survive the death of the process.** Sixteen frame processes had no common ground but the disk, so a FILE was made to carry a CONVERSATION between them — a lock to take turns, tmp+rename to publish, a lock-less fallback when the lock was taken, bounded retries when Windows refused. Every layer simulated by hand the one thing an operating system already does: **SERIALISE**. Three flaky bugs came out of that simulation in a single day.
📐 **MEASURED, Node 22.15.1: of the 68 builtin modules, ZERO expose an inter-process synchronisation primitive** — no named mutex, no shared memory, no semaphore. In C or Go you take a named mutex; here the ONE kernel primitive reachable from JavaScript is the **SOCKET**. That is not a preference, it is the whole reason this design is what it is.
✅ **PROVEN ON THE REAL ENGINE** (`state-daemon.test.js`): **16 real processes, one `once` document, delivered EXACTLY ONCE, with no lock — and ZERO file written**. The critical section has no mutual exclusion of ours because the kernel delivers one connection at a time onto a single-threaded loop. It is given, above us, for free.

🛑 **THE DISK IS A SAVE, NEVER A CHANNEL.** The snapshot is written by the SINGLE owner and read ONCE, at startup, **before the socket is open** — the only instant in a daemon's life when nothing else can exist. No concurrent reader ⇒ no lock, no window, **no retry on contention**: those existed only because a reader held the file while the writer wanted to replace it.
🛑 **BUT THE WRITE STAYS ATOMIC (tmp + rename), AND ITS REASON CHANGED.** It no longer protects a reader; it protects against a CRASH. A machine dying mid-write leaves a truncated file whatever the concurrency, and a corrupt save is worse than none. ⚠️ **NO `fsync`, and that is a DECISION**: it buys durability across a power loss, this state describes a LIVING session, and no session survives a reboot. Re-decide it — never inherit it — if this store ever holds something that must outlive the machine.

🛑 **THE BACKEND IS AN ARGUMENT, NEVER AN AMBIENT SETTING.** `pretool-core`/`emission-core` take `store` (and `withLock`) as parameters; absent ⇒ the historical disk modules, byte-identical, differentials green untouched. 🔴 **AN ENVIRONMENT VARIABLE WAS CONSIDERED AND REFUSED: env vars are INHERITED.** One leak and a spawned hook reads an EMPTY memory instead of the real state — every `once` delivered again, no error anywhere. An ambient switch on a state backend manufactures silent bugs.
🛑 **`store` AND `withLock` TRAVEL TOGETHER, never one without the other.** Memory + file lock = a cross-process lock protecting nothing (pure cost). Disk + empty lock = the 2026-08-07 production bug, deliberately reintroduced.
⚠️ **THE LOCAL NAME `withLock` IS LOAD-BEARING**: `state-write-under-lock-gate` proves no state write escapes the critical section by matching the SHAPE of the call site. Renaming it turned the gate blind — it went red immediately, which is its job ("an alias that hides a write is flagged"). **A guardrail is not worked around by choosing another identifier.**

📐 **ONE ADDRESS, THREE KERNELS** (`kernel-endpoint.js`, official `net` doc of the INSTALLED version): Windows → **named pipe** under `\\.\pipe\`, in the kernel's object namespace, *"Windows will close and remove the pipe when the owning process exits"* (zero cleanup of ours) · Linux → **ABSTRACT** unix socket (leading `\0`), *"not visible in the file system … disappears automatically when all open references are closed"* · macOS → a real socket **file**, the only one of the three leaving an entry, and only as a MEETING POINT. ⚠️ macOS has no abstract namespace — a property of that kernel, STATED, never emulated with a lock file.
🔴 **AND THE LINUX ADDRESS TRAVELS IN THE `@name` FORM — PAID IN CI 2026-08-20.** The kernel wants a leading NUL byte to make the socket ABSTRACT, but **an argv string may not contain one**: returning the kernel form made `fork(daemon, [address])` throw at once, and the whole daemon suite died on Linux while staying GREEN on Windows — no local run could have shown it. `@name` is the form Linux itself displays (`ss`, `netstat`), so the address stays printable, loggable and transportable; **`kernelAddress()` converts it at the TWO places the kernel reads it — `listen` and `connect` — and nowhere else.** Converting earlier puts the NUL back into something that gets passed or logged; converting in two places lets them drift, and for an address drifting means going SILENTLY DEAF. ⚠️ Idempotent on the other two systems, so no caller ever branches on the platform. ⚠️ **The first version of the test that guarded this was HOLLOW** — it compared the converted form to itself and passed BY COINCIDENCE on the broken code; what discriminates is asserting the transportable form carries NO null byte at all.
🔴 **TAKING THE ADDRESS IS ITS OWN PROBLEM ON macOS — FOUND BY CI, ONLY THERE (2026-08-20).** Windows removes its pipe when the owner exits, a Linux abstract socket disappears with its last reference, but macOS leaves a real FILE and Node unlinks it only on a clean `close()`. A daemon that is KILLED — the NORMAL case, since any code edit makes it exit — leaves a dead socket file and the next daemon cannot bind: `EADDRINUSE` for ever with nothing listening. ⚠️ **`leavesFilesystemEntry()` had NAMED that difference and nothing acted on it: a fact that is documented but not wired protects nobody.** ✅ `kernel-bind.js` clears it, and **never on a guess**: "the file exists so it is probably stale" would delete the socket of a LIVING daemon and leave every client knocking on an address nobody owns — silence, no error. The KERNEL answers instead, instantly: a connect that SUCCEEDS means someone is alive (`EADDRINUSE` stands); `ECONNREFUSED` means the entry is dead (unlink, then bind). No probe, no heartbeat, no delay as a verdict.
⚠️ **THE ADDRESS CARRIES THE REPOSITORY** (hashed root): two clones must NEVER meet on one daemon — different corpora, so one would answer for the other's documents. Hashed and not raw because a pipe name is length-bounded and a real path carries a user name (**this repo is public**).
⚠️ **ONE PROTOCOL, TWO TRANSPORTS**: an `http.Server` listens on a pipe exactly as on a port, and `http.request({ socketPath })` reaches it. So Codex — which has **no `http` handler** — becomes a CLIENT through `state-client.js` and loses the files, the lock and the flaky, while keeping its node startup cost. A second dialect would drift from the first.

🔴 **A BUILDER MUST NOT DECIDE WHETHER ITS CALLER LIVES OR DIES — FOUND ON macOS CI, 2026-08-20.** `createServer()` installed an error handler that THREW on `EADDRINUSE`, so a constructor imposed a lifecycle policy on every caller. `kernel-bind` attaches its own handler to inspect a possibly DEAD socket file — and this one killed the process first, three CI round trips before the cause was visible. **The house rule, broken in our own code: a core returns a verdict, the SHELL decides to die.** ⚠️ Invisible on Windows and Linux, because macOS is the only kernel of the three that leaves an entry behind. ✅ The guarantee is UNCHANGED — a second instance is still refused BY THE KERNEL, never by a PID file or a probe; what moved is WHO acts on that refusal (`main`, the executable shell, via `onAddressInUse`). ⚠️ `listenerCount` is deliberately not consulted: "is someone else handling this?" is a question about intent, and answering it by counting makes a guard depend on load order.
🛑 **NO DAEMON = AN IMMEDIATE FACT FROM THE KERNEL**, never a timeout: a missing pipe answers `ENOENT`, a dead socket `ECONNREFUSED`, at once. **No health probe, no heartbeat, no delay used as a verdict** — anywhere in this path, ever. ⚠️ What is NOT claimed: that the agent LEARNS it acted without its context. It does not; that absence is an OPEN work item and it will not be closed with a liveness probe.
⚠️ **AND THE DECISION IS INJECTED, SO IT IS TESTED WHERE IT IS NEVER TAKEN.** *Dead entry ⇒ clear · living entry ⇒ never touch* is only ever REACHED on macOS, so until `kernel-bind.test.js` existed it was exercised on ONE kernel out of three, and only indirectly through a spawned daemon: **breaking it would have shipped, unnoticed by Windows and Linux, to surface on somebody else's machine.** The probe and the unlink are parameters ⇒ the five branches are driven directly, deterministically, everywhere: free address (no probe, no unlink) · LIVING owner (nothing deleted, `EADDRINUSE` reaches the caller untouched — deleting there leaves a daemon running while every client knocks on an address nobody owns) · DEAD entry (cleared, then bound on the second attempt) · Windows/Linux (branch never entered) · any other failure (reported as is — cleaning an `EACCES` would hide a permission defect).
⚠️ **A CEILING IN THE SAME GESTURE AS THE WRITER** (`MAX_SCOPES`, LRU): a daemon runs for weeks and no payload ever says "this session is over". Unbounded growth is not a big number, it is a DATED outage. The bound is a COUNT, never a deduction about death — we keep the N most recently used and drop the coldest. **Reading counts as a use**, otherwise the busiest session is the one evicted.
⚠️ **FAIL-OPEN, identical to the disk store**: an unreadable or malformed snapshot yields an EMPTY state. `JSON.parse` succeeding is not the guardrail — the SHAPE check is. Worst case: one extra delivery. Never a broken action.
🔴 **AND ONE CEILING FOR TWO LIFETIMES WAS A SCALING DEFECT — CORRECTED 2026-08-21, sizing stated by the maintainer.** The keys of this map do not age alike: a `plan-` is born at EVERY tool call and dies with its action (**544 of 615 state files on the live install, 88 %**), while a `doc-seen-`/`turn-count-`/`remainder-` lives as long as its agent. Under a SHARED ceiling the ephemeral flood evicts the durable — one busy agent erases every other agent's memory in a few hundred calls, one re-delivered `once` at a time, in silence, and it gets WORSE with the number of agents. ⇒ **a budget PER CLASS**, so a plan can only ever evict another plan. Arithmetic written in the module and re-checkable: 3 durable keys per agent ⇒ 4096 ≈ 1300 simultaneous agents. ⚠️ The old comment said "512: far above any real fleet use" — written before the sizing existed. **A number nobody re-derives is how a limit ships unnoticed.**
🔴 **OPEN, MEASURED, AND DELIBERATELY NOT PATCHED TONIGHT: the snapshot is rewritten IN FULL on every state write.** That is O(total state) of disk per tool call. It was invisible while the ceiling was 512; at the sizing this project actually targets (hundreds of agents, ceiling 4096) it becomes megabytes written per action — and this machine already has a chantier open on SSD wear. It surfaced as a TEST TIMEOUT, not as a design review, which is the honest way to say nobody had measured it. 🛑 Do NOT "fix" it with a timer: the two authorities that exist are a COUNT (write every Nth mutation — a kill -9 then loses at most N-1 writes, i.e. N re-deliveries) and the daemon's own CLEAN EXIT, which it knows. Deciding between them changes the proven "the state survives a restart" property, so it belongs to the switch-over decision, not to a late-night edit.
