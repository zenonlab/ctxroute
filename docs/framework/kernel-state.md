# memory-store · kernel-endpoint · state-client — THE KERNEL SERIALISES, THE DISK ONLY SAVES (2026-08-20)

🔑 **THE RULE, AND EVERY LINE BELOW IS A CONSEQUENCE OF IT: the OS for what is ALIVE, the disk ONLY to survive the death of the process.** Sixteen frame processes had no common ground but the disk, so a FILE was made to carry a CONVERSATION between them — a lock to take turns, tmp+rename to publish, a lock-less fallback when the lock was taken, bounded retries when Windows refused. Every layer simulated by hand the one thing an operating system already does: **SERIALISE**. Three flaky bugs came out of that simulation in a single day.
📐 **MEASURED, Node 22.15.1: of the 68 builtin modules, ZERO expose an inter-process synchronisation primitive** — no named mutex, no shared memory, no semaphore. In C or Go you take a named mutex; here the ONE kernel primitive reachable from JavaScript is the **SOCKET**. That is not a preference, it is the whole reason this design is what it is.
✅ **PROVEN ON THE REAL ENGINE** (`state-daemon.test.js`): **16 real processes, one `once` document, delivered EXACTLY ONCE, with no lock — and ZERO file written**. The critical section has no mutual exclusion of ours because the kernel delivers one connection at a time onto a single-threaded loop. It is given, above us, for free.

🛑 **THE DISK IS THE TRUTH AGAIN FOR THE DURABLE CLASS (REWRITTEN 2026-08-22), AND ONLY A SAVE FOR THE EPHEMERAL ONE.** It used to be a save for everything: the snapshot was written by the SINGLE owner and read ONCE at startup, before the socket opened — hence no concurrent reader, no lock, no retry on contention. That held while the daemon OWNED the state, and it made its death destroy the fleet's memory. Now `doc-seen-`/`turn-count-`/`remainder-` go to `session-store` in the same gesture as the mutation, under the REAL lock, because a fallback client writes those same files; **and the snapshot carries BOTH classes, which is LOAD-BEARING and was nearly removed on 2026-09-20**. 🔴 A change made it write the durable class only, on the ground that losing a plan "costs a recomputation and never a re-delivery" — a sentence from a paragraph of THIS file that had gone stale the day before. **The whole suite passed: 2,798 tests, zero red**, because no cell drove "restart mid-action, then a late frame". 🔑 **THE TWO SNAPSHOTS ARE ONE GUARANTEE IN TWO FILES**: `daemon-invocations.json` restores the ARRIVAL ORDER across a clean death, so the daemon comes back knowing "this frame serves chunk 7", and the store snapshot holds the CONTENT that order points into. Keep the order, drop the content, and the late frames of an invocation in flight deliver NOTHING, silently. 🛑 **IF you change what either snapshot carries, you MUST ask what the other one still points at.** Sealed by the cell *"the memoised plan SURVIVES a clean restart"*, seen RED on exactly the change that had shipped green. ✅ **THE COST IS BOUNDED SINCE 2026-10-01 — IN BYTES, NOT ONLY IN KEYS**: the live file had reached 35.46 MB (96 % this class, `JSON.stringify` 183 ms) at less than half the KEY ceiling, because a count never bounds a size. `MAX_EPHEMERAL_BYTES` (16 MiB, UTF-8 bytes of the JSON the snapshot writes) now evicts the coldest plan whichever ceiling bites first, the running total is kept by the pure module on every write and deletion, and 🛑 **the YOUNGEST plan is never evicted, even alone above the ceiling** — it is the action in flight. 🛑 **IF you add a path that writes or deletes a `plan-` key, it MUST go through `memory-store-pure`** (`set`/`purge`/`evict`), or the total drifts from what is held; a cell re-adds it after every kind of mutation. Making the class DISAPPEAR from the snapshot stays what the cell above forbids. (`memory-store-pure.durableEntries`). 🔴 **THIS LINE SAID THE OPPOSITE UNTIL THAT DAY** — *"only `plan-` still lives in the snapshot"* — and it was measured on the LIVE production file: **35.46 MB over 1,823 entries, of which 1,787 `plan-` weighing 33.95 MB, 96 %**, rewritten WHOLE and SYNCHRONOUSLY on the thread that serves every `PERSIST_EVERY` mutations, `JSON.stringify` alone timed at **183 ms**. 🔑 The ephemeral class is HELD in RAM exactly as before — the memoised plan still serves the N parallel frames of one action, which is its whole reason to exist — it is simply no longer WRITTEN, because a restart MID-ACTION already breaks that action by another road (the invocation tables live in RAM, die with the process, and the frames landing afterwards re-serve their opening chunks). **Persisting a plan saved nothing that was not already lost.** 🛑 The DURABLE class is untouched: `doc-seen-`/`turn-count-`/`remainder-` are what prevent a document reaching one agent twice, and they travel write-through under the real lock as before.
🔴🔴 **AND THAT CRITERION IS NOT MET FOR AN INVOCATION IN FLIGHT — MEASURED IN PRODUCTION 2026-09-19, ON THE OPERATOR'S OTHER CONVERSATIONS.** Two states are involved and conflating them is how an agent certifies the wrong one: **`doc-seen-` says WHICH documents were delivered — disk, write-through, it survives** · **the three invocation tables say WHICH CHUNK the k-th arriving frame serves — RAM, and they die with the process.** A restart mid-action therefore keeps every document marked seen AND resets the arrival counter, so the frames that land afterwards are counted as the FIRST and re-serve chunk 1. **The document is not re-decided; the CHUNK is re-served.** That is a re-injection, it is visible to the agent, and nothing in this repository was looking for it. 🛑 **THE FAULT THAT PRODUCED IT IS THE ONE TO REMEMBER**: an agent photographed `doc-seen-` before and after a restart, found it intact, and declared "zero document re-delivered" — TRUE, and beside the question. **Proving the durable half and concluding on the whole state is this repository's oldest error shape, committed here by the agent that had repaired those very tables the same morning.** ✅ **CLOSED 2026-09-19 BY `invocation-snapshot-pure.js`, AND THIS PARAGRAPH ANNOUNCED IT OPEN FOR ONE DAY TOO LONG — IT MISLED AN AGENT ON 2026-09-20.** It read *"Neither is chosen; what is chosen is that the hole is written down"*, and that sentence was used as a REASON to stop persisting a state class. Nothing broke, because the two snapshots live in SEPARATE files — but the arrival order could just as easily have been inside the one being emptied. 🛑 **A doc that announces a hole somebody has since closed is more dangerous than an absent doc: it does not merely inform, it AUTHORISES.** ✅ What is true: the three tables are written to `daemon-invocations.json` on the process `exit` — the cost is paid AT DEATH, never in service, so the 32-disk-writes-per-action objection does not apply. `process.exit(90)`, the stale-code restart and therefore EVERY code delivery, is covered. ⚠️ **`SIGKILL` and a power loss are NOT**, and that residual is bounded: it degrades to exactly the behaviour described above, on a death that is rare instead of routine. Proven by `invocation-snapshot-restart.test.js` and its CONTROL (strip the exit handler from a COPY and the order does NOT survive).
🔑 **THE ACCEPTANCE CRITERION, STATED BY THE OPERATOR 2026-08-22 AND BINDING** (`daemon-is-a-cache.test.js`): *"we restart it forty billion times a day, and from the agent's point of view it is as if it had never restarted."* This daemon exits BY DESIGN at every edit of this repository — that is the NORMAL regime, so every fix shaped "die less" is wrong by construction; the death has to become FREE. **The daemon is a write-through CACHE, the disk is the TRUTH**, and the classification is PURE (`memory-store-pure.isWriteThrough`) — written in the I/O shell it would be mutated by nothing. ⚠️ The fallback is INDISTINGUISHABLE IN THE RESULT, not in the LATENCY: buying that speed back means holding durable state in RAM again. **Correct-but-slower, never fast-but-wrong.** ⚠️ The suite's CONTROL cell (a store built with no `durableStore` = the pre-2026-08-22 owning daemon) must FAIL the same sequence, or the acceptance cell proves nothing.
🛑 **BUT THE WRITE STAYS ATOMIC (tmp + rename), AND ITS REASON CHANGED.** It no longer protects a reader; it protects against a CRASH. A machine dying mid-write leaves a truncated file whatever the concurrency, and a corrupt save is worse than none. ⚠️ **NO `fsync`, and that is a DECISION**: it buys durability across a power loss, this state describes a LIVING session, and no session survives a reboot. Re-decide it — never inherit it — if this store ever holds something that must outlive the machine.

🛑 **THE BACKEND IS AN ARGUMENT, NEVER AN AMBIENT SETTING.** `pretool-core`/`emission-core` take `store` (and `withLock`) as parameters; absent ⇒ the historical disk modules, byte-identical, differentials green untouched. 🔴 **AN ENVIRONMENT VARIABLE WAS CONSIDERED AND REFUSED: env vars are INHERITED.** One leak and a spawned hook reads an EMPTY memory instead of the real state — every `once` delivered again, no error anywhere. An ambient switch on a state backend manufactures silent bugs.
🛑 **`store` AND `withLock` TRAVEL TOGETHER, never one without the other.** Memory + file lock = a cross-process lock protecting nothing (pure cost). Disk + empty lock = the 2026-08-07 production bug, deliberately reintroduced.
⚠️ **THE LOCAL NAME `withLock` IS LOAD-BEARING**: `state-write-under-lock-gate` proves no state write escapes the critical section by matching the SHAPE of the call site. Renaming it turned the gate blind — it went red immediately, which is its job ("an alias that hides a write is flagged"). **A guardrail is not worked around by choosing another identifier.** ⚠️ `lockModule.withLock(…)` is invisible to it too, which is why the daemon shell keeps a bare local alias.
🔴 **THE WRITE-THROUGH CROSSED A LOCK THE DAEMON WAS NOT TAKING — MEASURED AND CLOSED 2026-08-23.** Its `/emit` and `/turn` routes wrote the durable class with NO lock, justified as *"one process, one thread, one connection at a time: nothing to serialise against"*. That serialises the daemon's OWN callers and serialises NOTHING against a spawned peer — and since 2026-08-22 a peer writes those very files under the cross-process lock. **Two real processes on one `remainder-` key: 209 lost read-modify-writes out of 800; control with both writers locked, 0-1 of 800.** The write is atomic (tmp + rename) so nothing was ever corrupt — what vanished is a RECORDED DELIVERY, i.e. a document delivered twice, in silence. 🔴 **AND `/purge` MADE IT THREE, found the same day by TLC** (`specs/tla/State.tla`, run `StatePurgeWindow`): a compaction that takes no lock lets a peer holding a PRE-PURGE snapshot republish it, so a `doc-seen-` record is RESURRECTED and the document it names is WITHHELD for the rest of the session. All three routes — and the spawned PreCompact sweep — now take the REAL lock, at the SAME address as the spawned lane. 🛑 **THE ADDRESS HAS ONE OWNER** (`store-resolve.docLockDir` / `turnLockDir`, and `lockDirForKey` when only the KEY is known): a lock only serialises writers that take the same NAME, so two spellings are two locks and two locks are no lock. Never compose one by hand, and never pass a scope beside a key — a mismatched pair takes a lock that serialises nobody while looking correct. 🛑 **NO NESTING**: every route is synchronous and takes AT MOST ONE lock, which is what keeps `lock.js`'s "never nested" assumption true with N frames in one process. ⚠️ Lock unavailable ⇒ the route degrades exactly like the spawned shell (queue intact / turn uncounted), never a write without the lock. 🔑 **THE LESSON IS THE EXPIRY CLAUSE**: that exemption stated its own condition of validity, in bold, and still went stale with nothing going red — an invariant that depends on a fact elsewhere needs a judge that re-reads the fact.

📐 **ONE ADDRESS, THREE KERNELS** (`kernel-endpoint.js`, official `net` doc of the INSTALLED version): Windows → **named pipe** under `\\.\pipe\`, in the kernel's object namespace, *"Windows will close and remove the pipe when the owning process exits"* (zero cleanup of ours) · Linux → **ABSTRACT** unix socket (leading `\0`), *"not visible in the file system … disappears automatically when all open references are closed"* · macOS → a real socket **file**, the only one of the three leaving an entry, and only as a MEETING POINT. ⚠️ macOS has no abstract namespace — a property of that kernel, STATED, never emulated with a lock file.
🔴 **AND THE LINUX ADDRESS TRAVELS IN THE `@name` FORM — PAID IN CI 2026-08-20.** The kernel wants a leading NUL byte to make the socket ABSTRACT, but **an argv string may not contain one**: returning the kernel form made `fork(daemon, [address])` throw at once, and the whole daemon suite died on Linux while staying GREEN on Windows — no local run could have shown it. `@name` is the form Linux itself displays (`ss`, `netstat`), so the address stays printable, loggable and transportable; **`kernelAddress()` converts it at the TWO places the kernel reads it — `listen` and `connect` — and nowhere else.** Converting earlier puts the NUL back into something that gets passed or logged; converting in two places lets them drift, and for an address drifting means going SILENTLY DEAF. ⚠️ Idempotent on the other two systems, so no caller ever branches on the platform. ⚠️ **The first version of the test that guarded this was HOLLOW** — it compared the converted form to itself and passed BY COINCIDENCE on the broken code; what discriminates is asserting the transportable form carries NO null byte at all.
🔴 **TAKING THE ADDRESS IS ITS OWN PROBLEM ON macOS — FOUND BY CI, ONLY THERE (2026-08-20).** Windows removes its pipe when the owner exits, a Linux abstract socket disappears with its last reference, but macOS leaves a real FILE and Node unlinks it only on a clean `close()`. A daemon that is KILLED — the NORMAL case, since any code edit makes it exit — leaves a dead socket file and the next daemon cannot bind: `EADDRINUSE` for ever with nothing listening. ⚠️ **`leavesFilesystemEntry()` had NAMED that difference and nothing acted on it: a fact that is documented but not wired protects nobody.** ✅ `kernel-bind.js` clears it, and **never on a guess**: "the file exists so it is probably stale" would delete the socket of a LIVING daemon and leave every client knocking on an address nobody owns — silence, no error. The KERNEL answers instead, instantly: a connect that SUCCEEDS means someone is alive (`EADDRINUSE` stands); `ECONNREFUSED` means the entry is dead (unlink, then bind). No probe, no heartbeat, no delay as a verdict.
⚠️ **THE ADDRESS CARRIES THE DATA SERVED, NEVER THE FOLDER THE CODE LIVES IN** (hashed `stateDir`): two INSTALLATIONS must NEVER meet on one daemon — different corpora, so one would answer for the other's documents. 🔴 **IT HASHED THE CODE ROOT UNTIL 2026-08-24, AND THAT WAS A PRODUCTION DEFECT.** Since the daemon runs from a FROZEN copy while the spawned client hooks run from the working repository, ONE installation — same config, same `stateDir`, same corpus — got TWO addresses: the daemon listened on `\\.\pipe\ctxroute-6441e2fd2d17`, the clients knocked on `\\.\pipe\ctxroute-0149994ddb6c`, nobody errored, and the client lane fell back to disk in silence. Two code folders serving one `stateDir` are ONE installation; two state directories are TWO. Hashed and not raw because a pipe name is length-bounded and a real path carries a user name (**this repo is public**).
⚠️ **ONE PROTOCOL, TWO TRANSPORTS**: an `http.Server` listens on a pipe exactly as on a port, and `http.request({ socketPath })` reaches it. So Codex — which has **no `http` handler** — becomes a CLIENT through `state-client.js` and loses the files, the lock and the flaky, while keeping its node startup cost. A second dialect would drift from the first.

🔴 **A BUILDER MUST NOT DECIDE WHETHER ITS CALLER LIVES OR DIES — FOUND ON macOS CI, 2026-08-20.** `createServer()` installed an error handler that THREW on `EADDRINUSE`, so a constructor imposed a lifecycle policy on every caller. `kernel-bind` attaches its own handler to inspect a possibly DEAD socket file — and this one killed the process first, three CI round trips before the cause was visible. **The house rule, broken in our own code: a core returns a verdict, the SHELL decides to die.** ⚠️ Invisible on Windows and Linux, because macOS is the only kernel of the three that leaves an entry behind. ✅ The guarantee is UNCHANGED — a second instance is still refused BY THE KERNEL, never by a PID file or a probe; what moved is WHO acts on that refusal (`main`, the executable shell, via `onAddressInUse`). ⚠️ `listenerCount` is deliberately not consulted: "is someone else handling this?" is a question about intent, and answering it by counting makes a guard depend on load order.
🔴 **AND THE SAME CLASS CAME BACK THROUGH THE HOOK, NOT THE BUILDER — MEASURED ON THE macOS RUNNER 2026-09-23.** `main` passed the rendezvous server `onAddressInUse: (err) => { throw err; }`: the builder's `'error'` listener runs FIRST, so on macOS — the kernel that leaves the socket FILE behind — every restart threw before `kernel-bind` could probe the entry, and the daemon never came back after a code delivery (the child's stderr said so; `stdio: 'ignore'` had hidden it for weeks). ✅ `rendezvousLaneHooks()` (exported, both hooks are CLAIMS that do nothing): `EADDRINUSE` on this lane belongs to `kernel-bind`, whose `onError` still refuses a LIVING owner. 🛑 **If you give the rendezvous server a hook that acts on `EADDRINUSE`, you re-create this defect** — sealed by `rendezvous-restart.test.js`, seen red on both cells with the old hook.
🔴 **AND THE macOS ADDRESS MUST FIT `sun_path`, OR NODE TRUNCATES IT IN SILENCE — MEASURED THE SAME DAY.** Node's doc: a socket path is *"truncated to … 103 bytes on macOS"*. A 105-byte state path bound a TRUNCATED name, then `kernel-bind` unlinked the FULL one (`unlinkCode=ENOENT`, read in the journal) and re-bound into the leftover (`branch=rebind-failed`). ✅ `endpoint()` takes the FIRST rung that fits, in BYTES: the state directory, the user's temp directory, `/tmp`. Same name on every rung (the fingerprint still names the data served), deterministic, so the daemon and every client meet. 🛑 **If you move the rendezvous, you MUST keep it under `MAX_SOCKET_PATH_BYTES` and NEVER throw from `endpoint()`**: a spawned client calls it on every hook and must stay fail-open. Sealed by the five cells of `kernel-endpoint.test.js` (measured path, exact bound, bytes vs characters, last rung, OS temp), mutation 100 %.
🛑 **NO DAEMON = AN IMMEDIATE FACT FROM THE KERNEL**, never a timeout: a missing pipe answers `ENOENT`, a dead socket `ECONNREFUSED`, at once. **No health probe, no heartbeat, no delay used as a verdict** — anywhere in this path, ever. ✅ **AND THE AGENT NOW LEARNS IT ACTED WITHOUT ITS CONTEXT — CLOSED 2026-08-23, and NOT with a liveness probe**, which this line refused in advance and still refuses. On the `http` transport a dead authority runs NO code of ours, so no witness could live there; the one that speaks is `turn-count`, a SPAWNED client on the client lane, which is handed the kernel's error by `state-client` and says, once per context, what it OBSERVED — a refused connection — never a cause, never a verdict on another component. The canary stays structurally blind to this case (zero emissions ⇒ no denominator ⇒ `undecidable`), which is exactly why the witness is a SEPARATE one and not a widening of it.
⚠️ **AND THE DECISION IS INJECTED, SO IT IS TESTED WHERE IT IS NEVER TAKEN.** *Dead entry ⇒ clear · living entry ⇒ never touch* is only ever REACHED on macOS, so until `kernel-bind.test.js` existed it was exercised on ONE kernel out of three, and only indirectly through a spawned daemon: **breaking it would have shipped, unnoticed by Windows and Linux, to surface on somebody else's machine.** The probe and the unlink are parameters ⇒ the five branches are driven directly, deterministically, everywhere: free address (no probe, no unlink) · LIVING owner (nothing deleted, `EADDRINUSE` reaches the caller untouched — deleting there leaves a daemon running while every client knocks on an address nobody owns) · DEAD entry (cleared, then bound on the second attempt) · Windows/Linux (branch never entered) · any other failure (reported as is — cleaning an `EACCES` would hide a permission defect).
⚠️ **A CEILING IN THE SAME GESTURE AS THE WRITER** (`MAX_SCOPES`, LRU): a daemon runs for weeks and no payload ever says "this session is over". Unbounded growth is not a big number, it is a DATED outage. The bound is a COUNT, never a deduction about death — we keep the N most recently used and drop the coldest. **Reading counts as a use**, otherwise the busiest session is the one evicted.
⚠️ **FAIL-OPEN, identical to the disk store**: an unreadable or malformed snapshot yields an EMPTY state. `JSON.parse` succeeding is not the guardrail — the SHAPE check is. Worst case: one extra delivery. Never a broken action.
🔴 **AND ONE CEILING FOR TWO LIFETIMES WAS A SCALING DEFECT — CORRECTED 2026-08-21, sizing stated by the maintainer.** The keys of this map do not age alike: a `plan-` is born at EVERY tool call and dies with its action (**544 of 615 state files on the live install, 88 %**), while a `doc-seen-`/`turn-count-`/`remainder-` lives as long as its agent. Under a SHARED ceiling the ephemeral flood evicts the durable — one busy agent erases every other agent's memory in a few hundred calls, one re-delivered `once` at a time, in silence, and it gets WORSE with the number of agents. ⇒ **a budget PER CLASS**, so a plan can only ever evict another plan. Arithmetic written in the module and re-checkable: 3 durable keys per agent ⇒ 4096 ≈ 1300 simultaneous agents. ⚠️ The old comment said "512: far above any real fleet use" — written before the sizing existed. **A number nobody re-derives is how a limit ships unnoticed.**
✅ **CLOSED 2026-08-21 — the snapshot used to be rewritten IN FULL on every state write**: O(total state) of disk per tool call, invisible at the old 512 ceiling, megabytes per action at 4096+2048, and it surfaced as a TEST TIMEOUT rather than a design review. **TWO authorities, both FACTS, never a clock: a COUNT of mutations (`PERSIST_EVERY = 64`) AND the daemon's own CLEAN EXIT.** A count alone still writes far too often at low traffic; a clean exit alone loses everything on `kill -9`, and this daemon is killed on purpose at every code change. 🛑 **No timer, debounce or TTL on this path** — the budget admits only `distant` and `undecidable`, and neither fits a count the process itself holds.
🛑 **THE PROVEN PROPERTY CHANGED, AND IT IS SAID PLAINLY IN THE MODULE**: it WAS *"the state survives a restart"*; it IS *"the state survives a CLEAN restart ENTIRELY, and a `kill -9` loses at most the last N mutations"*. **Losing a mutation costs at most a RE-DELIVERY of a document — never a wrong action, never a corruption**, which is the only reason this trade is acceptable. N = 64 is bounded at BOTH ends (arithmetic in `memory-store-pure.js`, written to be refuted): below the 16 declared frames a full snapshot is still written once per action, i.e. nothing fixed; at 1024 one crash re-delivers a whole session's worth of documents. ⚠️ **The decision is PURE (`persistTick` / `shouldFlush`)** — Stryker never mutates an I/O shell, so a threshold written in `memory-store.js` would ship measured by nothing. ⚠️ Eviction does NOT follow this cadence: the ceiling bounds RAM, the snapshot bounds DISK — two budgets, two rhythms.
⚠️ **WHICH EXIT PATHS THE FLUSH REALLY COVERS.** `process.on('exit')` ⇒ a normal end, an explicit `process.exit(n)` — **including the stale-code exit 90, the daemon's most frequent death by far** — and an uncaught exception. 🛑 **NOT covered, STATED rather than implied: `SIGKILL`, and `SIGTERM`/`SIGINT` with no listener, which is what a supervisor's stop sends today** (Node terminates on the default action and `'exit'` never fires) — that path degrades to the bounded `kill -9` case. Closing it needs a SIGNAL HANDLER in the executable SHELL (`store.flush()` then `process.exit()`), **never in the store**: installing a signal listener suppresses Node's default termination, i.e. a builder deciding whether its caller lives. ⚠️ A test that kills with a signal measures the HARD death; proving a restart keeps its state requires the CLEAN stop.
⚠️ **THE MEMORY STORE SAYS WHAT IT LOSES (2026-10-04)**: a snapshot that cannot be SAVED, or that is CORRUPT on load, writes `daemon-error` (`memory-snapshot-save` / `memory-snapshot-load`); an ABSENT snapshot (first start) writes nothing. The behaviour is unchanged — empty memory, one re-delivery at worst — it is only no longer silent.
