# stale-code — the daemon never serves code that differs from the disk (2026-08-24)
🔴 **THE DEFECT, MEASURED, AND IT WAS AN INFERENCE.** `watchOwnCode` exited 90 on ANY `fs.watch` notification, concluding *"my code changed"*. An independent witness caught the event at the exact millisecond of a death on the FROZEN copy (18:47:19.717Z): `mtime` 13:46:20 **unchanged**, `ctime` 13:53:22 **unchanged**, **only `atime` moved**. Nothing had written to that copy since it was built and the daemon had killed itself **258 times**. Merely READING a file cost the whole fleet its injection window.
📐 **WHY — VENDOR DOCUMENTATION, DO NOT RE-RESEARCH IT.** libuv `src/win/fs-event.c` (v1.x) subscribes ReadDirectoryChangesW to eight filters INCLUDING `FILE_NOTIFY_CHANGE_LAST_ACCESS`, `..._ATTRIBUTES`, `..._SECURITY`, `..._CREATION`; all arrive as `FILE_ACTION_MODIFIED` ⇒ `UV_CHANGE` ⇒ Node's bare `'change'`. Microsoft `fsutil behavior` (page updated 2026-02-16): *"One hour is the maximum amount of time that NTFS can defer updating Last Access Time on disk"* — which is why a plain read killed the daemon up to an hour later, and why the deaths landed exactly one hour apart to the second. 🛑 **NOT a Windows quirk**: inotify `IN_ATTRIB` fires on timestamps and permissions, FSEvents raises `kFSEventStreamEventFlagItemInodeMetaMod`.
✅ **THE DECISION IS AN OBSERVATION NOW, AND IT NO LONGER DEPENDS ON NOTIFICATIONS AT ALL.** Before answering any request, the bytes this process COMPILED are compared with the bytes on disk. Differ, gone, or unreadable ⇒ exit 90, fail-closed. That also closes the symmetric hole all three vendors document — event LOSS, and all three prescribe the same remedy: ReadDirectoryChangesW buffer overflow / `ERROR_NOTIFY_ENUM_DIR` ⇒ *"you should compute the changes by enumerating"* · inotify `IN_Q_OVERFLOW` ⇒ *"rebuild part or all of the application cache"* · FSEvents `MustScanSubDirs`/`KernelDropped`/`UserDropped` ⇒ rescan. Comparing at the point of use IS that rescan, so the kernel's non-determinism stops mattering.
🛑 **THE BASELINE IS WHAT NODE COMPILED, NEVER A RE-READ — violable in one line.** Re-reading the sources at startup records the NEW bytes while the OLD code runs: the daemon then serves stale logic and compares itself clean for ever, a GREEN THAT LIES built on purpose. The hook sits on `Module.prototype._compile`, handed the exact string about to be compiled — no second read, hence NO WINDOW, and no reimplementation of Node's loader (`_extensions['.js']` would need one or the other). MEASURED on Node 22.15.1: the recorded string equals `readFileSync(file,'utf8')` byte for byte, shebang included.
🛑 **`src/hooks/http-daemon.js` IS THE ENTRY POINT — the OS units and the CI point THERE, never at `http-server.js`.** Four statements, and the ORDER is the guarantee: take `module` · arm the interception on a bare `Map` (so it needs none of our code) · require `stale-code.js` and hand the map over (it and `stale-code-pure.js` are therefore RECORDED — the two modules that DECIDE freshness are vouched for like the rest) · run `http-server.main()`. Inverting the last two hands over an empty map and the daemon refuses to serve. ⚠️ The ONE declared residual is the bootstrap itself, which is exactly why it holds no decision, no state and no I/O.
⚠️ **`node_modules` IS OUT OF SCOPE with its reason written**: an install is a deliberate act that restarts the service anyway.
🛑 **THE WATCHERS ARE KEPT AND DEMOTED TO AN OPTIMISATION.** Same derivation, same directories-not-files rule (git renames over the target, so a file watch follows the dead inode and goes silently deaf). A notification runs the SAME comparison; content really different ⇒ exit, otherwise ONE journal line `code-unchanged`. **The noise stays observable** — it was 258 deaths a day, and a guard nobody can see deciding is a guard nobody can trust.
🔴 **AND THE WATCHER'S `'error'` HAD NO HANDLER AT ALL** — the very event the kernels raise when notifications were LOST, and unhandled on an EventEmitter it is THROWN, so the daemon could die of the mechanism meant to protect it. It now verifies at once, then re-arms; a re-arm that fails records `watch-lost` and stops serving code we can no longer be told about.
🛑 **NO TIMER, NO DEBOUNCE, NO POLLING** — the comparison is synchronous and local, so the kernel and the disk already KNOW. A delay here would have no admissible motive (`temporal-budget.json` refuses both `local` and `simplicity`).
🛑 **DO NOT TOUCH `corpus.enableCache`.** It uses the same watch and it must keep exiting on nothing: a spurious invalidation there costs ONE re-read, where a spurious exit cost the fleet its window. Never "harmonise" the two — they answer opposite questions on purpose.
