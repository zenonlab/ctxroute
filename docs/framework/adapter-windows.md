# service/ — the Windows dedicated adapter (WINDOWS ONLY, 2026-09-03)

🔑 **WHY IT EXISTS.** libuv calls `WSAIoctl(SIO_TCP_INITIAL_RTO, MaxSynRetransmissions=0)` whenever the destination passes `uv__is_loopback()` — a LITERAL test on the address bytes (first byte 127, or exactly `::1`). On such an address Windows NEVER retransmits a lost SYN, so an ordinary client micro-stall loses every connection in flight at once. Binding outside `127.0.0.0/8` does not defeat that test: it LEAVES the domain where it applies, and libuv answers correctly for the new address. **Never call this a workaround** — that framing was made and corrected on 2026-09-02.
🛑 **WINDOWS ONLY.** `SIO_TCP_INITIAL_RTO` is a Winsock ioctl with no Unix counterpart (verified in libuv `src/unix/tcp.c`, 2026-09-02). Linux and macOS need none of this and are socket-activated anyway. The published default stays `127.0.0.1` on all three: **the OS difference lives in the DEPLOYMENT PROFILE, never in an `if (win32)` in the engine.**
🛑 **THE SetupAPI IS THE ONLY ADMISSIBLE PATH — read at Microsoft, 2026-09-02, not probed.** `hdwwiz` is the documented GUI and needs a human · `devcon` is WDK-only and not redistributable · `devgen` is WDK-only AND its own page says *"not allowed to be redistributed and should not be used for production scenarios"*. And the two tools Windows DOES ship cannot do it: `netcfg` knows only the classes `p|s|c` and an adapter is none of them; `pnputil` manages driver PACKAGES and has no verb that creates a device. `netloop.inf` ships with Windows, so no third-party driver is ever installed.
🔑 **RECONCILIATION, NEVER AN INSTALL SCRIPT.** The address is DECLARED once (in the config, and only when the config is silent — an operator who chose one is never overruled) and the machine CONVERGES towards it. Re-running always converges. "Detect and alert" was refused: it puts a human back in the loop.
🛑 **PRIVILEGE SEPARATION.** Creating an adapter needs elevation; serving frames does not. The boot task runs as SYSTEM, does one thing, exits — so elevation is paid ONCE at registration and never at any boot. It triggers at BOOT because the address must exist before the daemon's LOGON task. 🛑 It points at the FROZEN copy: a task with those rights may never run code that agents edit.
🔴 **THE METRIC IS PINNED TO 9999, AND THAT IS NOT COSMETIC.** Windows gave this adapter an automatic metric of 25 against the Wi-Fi's 35 — LOWER means HIGHER priority, so a virtual adapter leading nowhere outranked the real one. It is the exact lever behind the two failures documented on Microsoft Q&A (a broken phone hotspot; pings answering "General failure"), both of which also came from configurations this design forbids (a default gateway on the adapter; the address `172.168.1.254`, which is NOT private and which the engine refuses). `AutomaticMetric` must stay OFF or Windows recomputes it at the next boot.
⚠️ **`/32`, NO GATEWAY, DHCP OFF, DNS REGISTRATION OFF** — the daemon has NO authentication, so the address IS the boundary. A `/32` publishes no subnet route; nothing on the LAN has a path to it.
🛑 **NEVER SPELL A LONG COMMAND-LINE OPTION INSIDE THE TASK XML COMMENTS.** XML forbids a double hyphen anywhere in a comment and a real parser rejects the WHOLE file — measured on the installer's very first real run. `service-units-gate` catches it, derived from the directory.
🛑 **NEVER READ A VALUE BY REQUIRING A SHELL.** The installer read the port with `require(http-daemon.js)`, a module that STARTS a daemon when loaded: the read bound a second instance, hit `EADDRINUSE` and exited 1 — on the RE-install path only, which is the one anyone exercises twice. Values come from `paths.httpEndpoint()`, which resolves and starts nothing.
✅ **THE SYN CLASS IS CLOSED BY CONSTRUCTION — do NOT hedge it (corrected 2026-09-03).** The ioctl sits INSIDE the `if (uv__is_loopback(...))`: outside it we are on the ORDINARY TCP path, the one every Node connection to a real network takes on Windows, so the fix inherits the reliability of the most-travelled path in the stack. Measured inside ONE session, both addresses, same client and load: `127.0.0.1` **2,061 failures / 14,777** against **128 / 15,712** on this adapter, all 128 inside the 24-second switch-over window and ZERO outside; a later session ran 3 h 18 and 8,015 POSTs with zero. 🛑 What stays unproven is a DIFFERENT question — whether some OTHER failure exists on the new address — and it must never be smuggled in under this one. No bench here reproduces the ORIGINAL defect either (6,400 connections on each address, zero loss on both). Persistence WAS proven without rebooting (adapter cycled: address gone, then back with a `Manual` origin); the boot ORDER was not. And whether the KM-TEST adapter is fit for production is a DOCUMENTED BLANK — Microsoft states neither approval nor prohibition. The exit exists and is one config value away: the `command` lane opens zero connections, so the class does not exist there.
🛑 **DELETING THIS ADAPTER NOW KILLS THE DAEMON, ON PURPOSE (2026-09-03) — and that is the SAFE outcome, not a regression.** Without the address the port bind fails with `EADDRNOTAVAIL`, the port lane records `bind-failed` and the process DIES. Until that day it did the opposite and it was far worse: the handler knew only `EADDRINUSE` and a registered `error` listener SUPPRESSES the throw, so the daemon stayed **ALIVE AND DEAF** — and, still holding the kernel rendezvous, it squatted the address its own replacement needed, so every supervised restart died on `EADDRINUSE`. **A deaf daemon blocks its own relief, for ever.** ⚠️ Recovery is owned by the pieces that can see the address: the boot task recreates it, the supervisor restarts the daemon. The daemon never retries and never reconciles — from inside, it cannot tell whether the address is coming back.
🔑 **AND NO OTHER PLATFORM GETS AN ADAPTER — a DECISION, never an omission to be «fixed» later.** The defect it exists for is ABSENT on Linux and macOS: `SIO_TCP_INITIAL_RTO` is a Winsock ioctl and libuv's `src/unix/tcp.c` carries nothing about retransmission, RTO or loopback. Building a portable adapter abstraction would pay for a problem that cannot occur there — and an interface written with ONE implementation in view only recopies its dialect under other names. ⚠️ The portable seam already exists and is the right one: the address is a single config value resolved at `paths.httpEndpoint()` (published default `127.0.0.1` everywhere, only the Windows deployment profile pointing elsewhere), and installation is ONE SCRIPT PER OS. The day another platform needs an adapter it gets its own script, and nothing here is refactored.
