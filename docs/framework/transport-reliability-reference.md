# Transport reliability — the full history, measurements and incidents

ON-DEMAND page (never re-injected). The short invariants live in the skill (`## What this framework can and cannot guarantee`, `## Multi-frame transport`, `## Canary`); here is the full WHY — dated incidents, exact numbers, dead ends — for whoever ports the mechanism or doubts a claim. Goal: zero ambiguity for the agent who comes next, and no re-litigating a question already answered by measurement.

## Routing vs transport — the founding distinction (settled 2026-08-30, never re-litigate)
Confusing routing (100% deterministic, proven on 400,000+ exhaustive cases) with transport (delivery over a channel that may drop messages) cost a whole session and produced a promise this project cannot keep. **Guaranteed delivery is mathematically impossible** — the Two Generals Problem: no protocol over a lossy channel can guarantee a message arrived. Not "hard in 2026" — impossible, permanently. Dropping to a lower-level language changes nothing: both limits sit ABOVE us (the 10,000 c per-output cap is Claude Code's; a lost loopback connection is the Windows kernel's). What TCP actually provides is retransmission + notification, never delivery — hence *at-least-once*, *exactly-once with acknowledgement*; nobody writes *always*.

We cannot even do what TCP does: Claude Code opens the N frame connections and receives the failures, the daemon is the SERVER. There is no retry inside one action. An action's capacity is FIXED at `frames that arrived × 10,000 c`; whatever exceeds it can only reach the NEXT action — by then the agent has already acted. Deferral is a consolation, never a repair.

The guarantee that IS reachable, and the one safety engineering actually uses: *the agent never works without the knowledge it is owed.* A railway brake does not guarantee the signal arrives; it guarantees a missing signal STOPS the train (`enforce` ⇒ `deny`). Lower the loss rate first, arm the brake second — a brake on a 50% loss rate blocks every other action and gets unplugged.

How to talk about this: never sell "nothing is ever lost" — false, and it will be measured false. Say what is true: *routing is exact, transport can drop, and we detect it*. The thing that would kill this project is not a drop, it is a SILENT one.

## One injection window per tool call (settled 2026-08-30 against all three harnesses' official docs)
Structural, not a version detail: the harness is the CLIENT (POSTs to `type:"http"`), the daemon is the SERVER. A server cannot call back a client that is not calling — no re-open, no extra connection, no re-contact request, on any release.
- Claude Code hooks reference (read 2026-08-30): *"Claude Code cancels a `command`, `http`, or `mcp_tool` hook that reaches its `timeout`, discarding the hook's output"* and *"A timed-out … hook doesn't block the tool call … don't count on a stalled hook to act as a gate."* Failure is TERMINAL for that call. Codex and Gemini CLI document no retry either.
- No other channel exists between a hook firing and the tool executing — no server retry, no partial response, no streaming, no second round trip. Undocumented in all three: an absence measured, not a search gap.
- `PermissionDenied` + `hookSpecificOutput.retry: true` is Claude Code's AUTO-MODE PERMISSION system, a DIFFERENT event from a `PreToolUse` hook returning `deny` — not a hook retry.

### The loss is no longer permanent (closed 2026-08-31, `carryover-pure.js`)
The paragraph above stays true (a frame that never connects is lost FOR THAT TOOL CALL), but until this date the CONTENT promised to that frame was DROPPED: `emission-core.emit` persisted only what overflowed the LAST frame of a plan and ran ONCE per invocation, while `doc-seen-` already recorded the document delivered — no later action re-decided it. MEASURED: 10 of 32 connections on one action, chunks 11..19 of 19 never seen again, ever.
The mechanism, and it invents no fact: when an invocation decides its plan it HARVESTS the not-yet-served segments of the other pending invocations of its scope and carries them itself. A harvested invocation serves nothing more (ownership MOVES, never shared — atomic because the daemon is single-threaded, no lock, no timer, no liveness probe). Nothing asks whether an invocation is FINISHED (not an available fact); only two facts are used: a frame arrived, and a new invocation is deciding. HTTP lane only: the spawn lane's N processes really do all run, byte-identical there.

### The most reliable configuration (operator, 2026-08-31)
Not "the `command` lane" alone — a PAIR: **one single `command` declaration** + **a harness with NO output cap**.
- Codex satisfies both: `additionalContextLimit = 0` = *"pass the handler's complete additional context directly to the model"* (measured in the 0.146.0 binary) ⇒ one declaration, one process, zero chunking, zero simultaneous connections. The whole transport-defect class is ABSENT by construction. Price: ~330 ms process start, once per action.
- Claude Code does NOT: its cap is ~10,000 characters per output, so a single declaration there SPILLS to a file with a 2KB preview (measured, shipped and reverted the same day). N declarations stay required, and the `http` lane's burst comes with them. Never read "one declaration" as advice for Claude Code.
- Why this matters beyond us: the framework's reliability is a property of the DEPLOYMENT, not of the framework. Catastrophic-error contexts: pick the pair above, the class doesn't exist. Speed-first contexts: take the `http` lane, accept a bounded, measured, NON-SILENT loss.
- What this buys and does not: the agent may still act ONCE without knowledge it was owed — deferral is a consolation, never a repair. What ends is the SILENCE.

### The loopback saga (closed 2026-09-03) — kept ONLY because it explains a datacentre exception
`anthropics/claude-code` #29963 asks for one retry on the connection loss and is CLOSED `NOT_PLANNED`. The real fix was never a retry: *must we stay on a LOOPBACK address?* libuv calls `WSAIoctl(SIO_TCP_INITIAL_RTO, MaxSynRetransmissions=0)` whenever the destination passes `uv__is_loopback()` (first byte 127, or `::1`) — Windows then never retransmits a lost SYN, so a client micro-stall kills every connection in flight at once. Binding outside `127.0.0.0/8` doesn't defeat that test, it LEAVES the domain where it applies. Confirmed by a .NET client losing 0% against the same daemon, and a bare Node server losing as much as we did.
MEASURED 2026-09-03: `127.0.0.1` 2,061/14,777 failed; `10.87.87.1` 128/15,712, ALL inside the 24-second switch-over, ZERO outside. A later session: 3h18, 8,015 POSTs, ZERO. The class is closed BY CONSTRUCTION (the ioctl sits inside `uv__is_loopback()`; outside it we're on the ordinary TCP path every Node connection to a real network takes on Windows), not by that count alone.
**Production has served `10.87.87.1` on four ports since 2026-09-03; the loopback class is CLOSED and survives only to explain why a datacentre deployment (daemon on another host) is outside the defect by construction, Windows Server included.**

### The residual (~0.9–1.6% of POSTs, no diagnosed cause, closed 2026-09-20)
Stationary over weeks on the non-loopback address. Known only: no first loss under TWO HOURS of session ever; volume alone explains nothing (7,744 POSTs lost zero, 448 lost 9); something accumulates, unidentified. Eliminated by measurement (2026-09-20), never re-test: ephemeral-port exhaustion (194/64,511 used), a dead daemon (80 probes, 80 served, pid unchanged), the accept-queue cap alone (quadrupling sockets didn't move the residual). Never measured anywhere but the operator's own loaded workstation (16 MCP servers, browsers, test suites) — reaches ~2% under saturation, 128 POSTs lost ZERO at rest.
Closed at the vendor source: Microsoft's `listen` reference — *"If a connection request arrives and the queue is full, the client will receive … WSAECONNREFUSED."* A resource limit, not a theorem. The queue is emptied by a client we do not own; `anthropics/claude-code` #29963 asks for one retry, CLOSED `NOT_PLANNED` (re-verified 2026-09-20). Not ours to close. Do not reopen unless the rate climbs and does not come back.
The class does not exist for a client we write: `ECONNREFUSED` only happens while ESTABLISHING a connection; an industrial client establishes once and reuses (keep-alive, a pool, HTTP/2 multiplexing) — 32 frames then cost ONE accept, ever. The burst is a property of Claude Code's hook design (a ~10,000 c cap per hook output ⇒ N declarations ⇒ N parallel connections it opens itself), never of HTTP. The `command` lane is NOT the industrial answer — it's local by construction (spawns a process), cannot live on a server or scale in a datacentre. HTTP is the only lane that scales horizontally; the burst is a constraint to live with, never to trade away.

### The burst itself (unchanged by the loopback fix)
What used to break on `127.0.0.1`: a burst of ~38 simultaneous hook connections from an interactive session lost connections — 30, 22, 32 `ECONNREFUSED` in three one-second bursts, triggered by 12 parallel tool calls / spawning a subagent. Normal use (1-5 parallel calls) was clean.
Eliminated by measurement, never re-test: the daemon (fresh copy 384/384, production zero deaths), a bare 10-line Node server (384/384), accumulated state (2.9MB copied in, 384/384), two concurrent clients (384/384), daemon uptime, socket leak (0 sockets held by old sessions), the statusline, the frozen release code. Six hypotheses died in one night; the operator's own "it gets worse with load" was the only one left standing.
"Client age" was eliminated on a single observation and should not have been — measured over 7 sessions, delay to FIRST loss: +2h15, +2h17, +7h43, +9h19, never under two hours. Sessions of 4,192 and 7,744 POSTs lost ZERO; a session of 448 lost 9. Volume alone does not explain it. Lesson: a single observation may close nothing; a "never re-test" imperative baked into an injected doc stops every later agent from checking, and that is a process failure worse than the anecdote itself. Consequence for any future A/B here: measuring the first two hours proves nothing.
Each failure costs money beyond the lost knowledge: the failure text differs from the success text, changing the prompt prefix, changing the cache key — the whole turn is recomputed. Reported ~$45 for ONE failure on a 1M context.
Refused fixes, do not re-propose: fewer declarations (breaks the one-gesture promise), delivering over several gestures via the deferred queue (same breakage), making the burst independent of payload size (same thing, restated). The one unexplored, unmeasured way out: a lane that doesn't fan out into N simultaneous connections (`command`, or possibly `mcp_tool` whose output cap is unknown — measure it first).
How to see any of this at all: `hook error` lines are written nowhere in the transcript, only on screen. `--debug hooks --debug-file <path>` is the only way to count them; `claude-core.bat` now arms it every session. Read a log only after it is flushed — a premature read once returned zero where 30 failures had just occurred.

## Multi-frame transport — the full protocol history
See the skill for the operating rule (2 paths + queue). This section is the RFC-grounded design rationale and the incident history.

**Why we did this**: the harness bounds injection size; beyond it, it files the content away and shows only a preview, without telling the producer. Docs announced "not injected" every turn, skills never delivered.

**The protocol, taken from the existing, nothing invented** — RFC 2046 `message/partial` and RFC 6455 WebSocket both solve "a message too big for its channel" with the same three pieces of information: whose it is (`id` / the connection / our `###END:xxxx###` marker), where it goes (`number` from 1 / continuation frames / `CHUNK j/m`), when it's complete (`total` / FIN bit / the `m` of `j/m`). Plus: cut on line boundaries (RFC 2046), strict order never interleaved (RFC 6455). This is TCP/MSS segmentation, not IP fragmentation (RFC 8900's 9 fragility causes are all middleboxes; none exist here). No automatic ceiling discovery (RFC 8899/PLPMTUD needs a feedback signal that doesn't exist here) — instead: conservative floor + negotiation when an authority exists. Claude Code: internal ceiling undocumented, we take a margin (8,000 under the measured 10,000). Codex: `additionalContextLimit` declared by us at `0`.

**Bandwidth history**: 12 frames until 12/08, 16 until 22/08, 32 since. Capacity = frames × 7,684c = 245,888c at 32. The ceiling is the CLI display (one entry per declaration) — 32 reads fine, 100 doesn't (tried and cancelled the same day). A 24-hour advocacy for "one single declaration" was FALSE and cancelled: the framing error was mistaking display order for the requirement, which is "complete context before the next tool call" — at 1 frame a 53,830c skill spread over 8 actions, the agent acting 7 times on partial knowledge. Ordering is guaranteed by NO harness (hooks run in parallel, aggregation unspecified) and cannot be forced. A real duplicate-chunk bug (closed 2026-08-07) traced to the lock-unavailable fallback deciding with an EMPTY state, re-emitting an already-delivered `once`; fixed by having the fallback READ the state while still writing nothing. 1,096 tests didn't see it — a degradation path tested only with an empty state is not tested. The `http` lane went live 22/08/2026 (measured 5,300ms → 182ms per action).

**Capacity alarm** (07/08/2026): a deferred doc names the setting (`frames`) on the LAST frame only. Closes "nothing measures throughput" — the degradation used to be silent.

**Cost measurement**: at 12-16 frames (~5.3s), 12 idle `node` processes cost ~4s; the framework itself is 4% of the cost, node startup is 96%. Optimizing collection was a measured false lead (03/08/2026). The only real lever is N, and lowering it caps what can be delivered.

**Codex-specific incidents**: `additionalContextLimit` measured 0 occurrences in binary 0.144.6, 18 in 0.146.0 — a documented key that was not in the installed binary, so the declaration was inert for two days. Omitted = default 2,500 tokens, silent disk spill. A false fix (`PostCompact` wiring on Codex) was nearly shipped on the premise that compaction was undetected there — it's covered twice already (`PreCompact` + `SessionStart` with `source: compact`), and adding `PostCompact` would double-deliver every session doc after a compaction. Gemini CLI: `PreToolUse` doesn't expose the channel at all — a capability hole, not a size one.

**Output cap incident** (2026-08-31): a first measurement said the cap was gone (a hook returned 1,500,000 characters). That measurement was real and its conclusion was false — wired at a 400,000c budget with 1 frame, the harness SPILLED the content to a file with a 2KB preview instead of cutting it. The agent quoted markers because it could still reach the file, not because the text reached its context. The ~10,000 floor stands; observed spill at ~14.8KB. Lesson: measure whether the harness puts text IN THE CONTEXT via a real injection, never through a probe that only proves the response left the server.

**Two silent defects closed 2026-08-06**: (1) a skill delivered in 7 chunks showed 7 identical badges and the maintainer read it as the framework "running away" — fixed by carrying `#j/m` in the chunk id, composed once in `pretool-core.js`. A pre-existing bug (the `[source:]` tag lives at the document's END, so only the last chunk carried it, and `docLabel` fell back to displaying the seal footer as a title) was found by the anti-inertness test built for this fix. (2) `note: |` silently swallowed its YAML block lines with `validate` green — fixed by teaching `parse()` real YAML block syntax; a guard placed in `validate()` was removed the same day because only `parse()` sees the next line, hence only it can lift the ambiguity — placing a guard where the information no longer exists forbids the healthy.

**Three joint guardrails on the emission queue** (else it loops forever): the announcement counts documents (dedup, cites 5 max); a progress guarantee forces ONE chunk out even if nothing fits cleanly (delivering beats describing); `fragment` drops the chunk header when capacity can't carry it. Nothing is ever "too small" either — a 2-char content leaves as-is, and when the budget can't even carry the seal, the envelope yields, never the content (a real 03/08/2026 bug used to emit zero docs AND blame `--frames N` simultaneously).

## Canary — incident history
See the skill for the operating rule (alive/dead/undecidable via `[source:` count). History:
Wired on both harnesses since 07/08/2026, and the Codex port cost no file — a plan to reverse-engineer the Codex transcript schema was abandoned on documentary evidence (*"the transcript format isn't a stable interface for hooks and may change over time"*) in favor of counting our OWN emission counter and searching for our OWN `[source:` substring — zero harness dialect, one shell for both products.
The displayer (the maintainer's statusline) is a failure point OUTSIDE the repo, and it failed once: it pointed at the repo's pre-rename name for 3 days, canary verdicts written for nobody, the fail-open `catch` masking everything.
Reading is bounded to 2MB from the end (a real 104MB transcript: 524ms whole, 5ms the tail). Threshold = 25 emissions as a SAMPLE size (redone from counting tool calls, based on 13 real compactions, 94→335 injections in between). The transcript is asynchronous (official doc) — an injection that just landed may not be there yet; this forbids lowering the threshold to 1-2.
A real self-contradiction was found and fixed 07/08/2026: the skill claimed the harness dialect lived in a Claude call-marker constant that had ALREADY been removed nine lines above in the same file — found by grepping the deleted literal, not by re-reading. Lesson: a doc doesn't pile up, it gets rewritten.
Defect ㉘ (found by measurement, not a test): the numerator counted every occurrence of `[source:` including the literal living in `canary.js`'s own comments and 64 fleet docs that merely CITE the marker — an agent reading one of those docs (the exact action of investigating a dead injection) turned the canary green. Fixed: only a label of emitted FORM counts. Not the complete fix: 4 fleet docs cited a `.md` directly — closed by removing the hardcoded tags, sealed by a zero-exemption lint rule.

## The purity gates were inert (real bug, 2026-08-03)
`lib-pure-must-stay-pure` — the repo's oldest architecture gate — could not turn red: a `require('fs')` at the top of `lib-pure.js` passed GREEN. ALL `*-must-stay-pure` rules were decorative. Cause (official dependency-cruiser doc): `includeOnly` filters the DEPENDENCIES too, so `fs`/`path`/`child_process` never entered the graph (41 modules/99 deps before, 47/143 after). Sealed by `deps-purity-gate.test.js` (static, derived from the rules + real sabotage on a COPY, never a real file — the first version brought down 38 unrelated tests). Never `npx` from a tmpdir for this kind of sabotage: it fetches over the network.
