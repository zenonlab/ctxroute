# http-server.js — the SAME gate, served over a socket (LIVE since 2026-08-22)

🔴🔴 **READ THIS BEFORE ANY THEORY ABOUT THE DAEMON BEING SLOW. THE LAG IS THE CLIENT, AND IT IS MEASURED: on 200 consecutive stalls, 100 % of the elapsed time is the daemon WAITING FOR THE CLIENT to finish sending its body, and 0 % is work — `handleMs` stays at 1-3 ms while the loop runs 500 ms behind.** A client that stalls for half a second is ORDINARY: we are the SERVER, the harness owns the client, and nothing on this side makes somebody else's socket write faster. 🛑 **DO NOT RE-DERIVE THIS, AND DO NOT RE-MEASURE IT** — it has been established three times and re-derived wrongly three times, each time by an agent that had this file in its context. ⇒ **THREE CONSEQUENCES, AND THEY KILL THREE TEMPTING REMEDIES:** ① **more CORES change nothing** — Node's own documentation says workers *"do not help much with I/O-intensive work"*, and waiting is not computing, so a worker pool moves 2 ms and leaves the 500 ms where they are ② **more SOCKETS buy CAPACITY whose benefit is NOT ESTABLISHED** — say it that way and never "they change nothing": the queue link has been buried and withdrawn once already (`peakConn` read 32 on one calm minute, then **254 against a 232 ceiling** twelve seconds before a live burst on 2026-09-18), and the current journal maxes at 122. 🛑 **AND THE COUNTER CANNOT SETTLE IT EITHER WAY**: it increments on the `connection` event, i.e. on ACCEPT, so a queue that is full while the loop is starved accepts nothing and is counted as nothing. A low reading is therefore not evidence of a healthy queue — it is the shape a saturated one also takes ③ **the ONE lever that exists on our side is to stop making the harness open 32 connections at once** — that is the `command` lane, one process and zero simultaneous connections, which is exactly why Codex has never seen this. 🔑 **AND THE OBSERVATION NOW CARRIES THE ATTRIBUTION**: `loop-block` logs `bodyMs`/`freshMs`/`handleMs` beside `elapsedMs` since 2026-09-19, because the version that logged `elapsedMs` alone was read as "the handler is burning CPU" and a whole architecture was designed on that misreading. **A line that cannot say where its time went will be read as blaming whoever is nearest.**

🛑 **THE CAP IS PER OUTPUT, NOT PER PROCESS ⇒ N DECLARATIONS STAY REQUIRED.** HTTP changes their PRICE (~330 ms of node startup each → one local POST), never their NUMBER. Collapsing to one declaration drops an action's capacity to a single frame and makes the agent act on partial knowledge.
🛑 **KEEP `lock.js`.** "One daemon, therefore no lock" is the trap: Codex keeps spawning real processes against the same state files, and other sessions exist. 🔴 It was sprung on `/emit`, `/turn` and `/purge` — **209 lost read-modify-writes out of 800** on one key, i.e. a document delivered twice in silence. All three take the REAL lock at the SAME address (`store-resolve.lockDirForKey`): a route may never compose a lock name, and two spellings are two locks, which is no lock.
🛑 **THIS PATH MUST STAY SYNCHRONOUS, and at most ONE lock at a time, never nested.** `lock.js` busy-waits assuming short-lived callers; here N frames land in ONE process, so an async core lets request A hold the lock while B spins for the full timeout — a self-deadlock that reads as a slow daemon.
🛑 **NO `deadline.arm()` here** — a deliberate inversion of the rule every other shell follows: the deadline kills zombie hook PROCESSES, a daemon is meant to outlive its request. The bound belongs to the harness `timeout`.
⚠️ **THE DIALECT IS NOT REIMPLEMENTED**: the response JSON comes from `doc-inject.output()`, the function the spawn lane uses. A second copy is a twin that drifts.
🛑 **A BIND ERROR IS NEVER SWALLOWED.** A registered `error` listener SUPPRESSES the throw, so every code the builder did not know left the daemon **ALIVE AND DEAF** (`listening === false`, no exception, no log) — measured on Node 22.15.1 with `EADDRNOTAVAIL`. ⇒ a code leaves quietly ONLY if a caller CLAIMED it by name (`onAddressInUse`, `onLaneLost`); anything unclaimed RETHROWS. **Enumerating what to die on is how a guard is born stale.**
🛑 **AND THE TWO LANES DECIDE THE OPPOSITE, DELIBERATELY — never "harmonise" them.** The rendezvous degrades ONE lane and keeps serving. The reverse is not symmetric: a port-less daemon still takes the rendezvous, so it **squats the address its own replacement needs** and every supervised restart dies on `EADDRINUSE`. The PORT lane therefore records `bind-failed` and DIES, handing recovery to the supervisor and the boot task. It never retries — that would be the reconciler's job, done from the one place that cannot see whether the address is coming back.
🛑 **EXIT CODE 90, for portability not style**: a supervisor restarts on FAILURE only. 🔴 It was 75 for one hour and 75 is a TRAP — systemd's own manual declares *"Exit status 75 (TEMPFAIL), 250 … are considered clean service terminations"*, so copying a manual's example would have turned the stale-code restart into "job done". 90 sits outside every alias: impossible by construction, not discouraged by a warning.
⚠️ **NOTHING HERE INFERS LIVENESS.** No health probe, no heartbeat, no timeout as a verdict — a dead socket answers `ECONNREFUSED` instantly, and death is an OS EVENT. 🛑 The hook must NEVER start the daemon: that is how orphans are born, and it is the OS's job. ✅ It may ASK the OS supervisor (2026-09-29): `daemon-ensure.js` runs the Windows task (a no-op while it runs), and an `on-demand` daemon leaves on idle — 🛑 SI you add a server, lane or thread here, you MUST hand it `activity`, or the daemon leaves while it serves (`lifecycle.md`).
🔴 **NO DAEMON = TOTAL SILENCE, MEASURED.** Nothing listening ⇒ the tool runs normally, no error surfaces, the agent never learns it acted without its knowledge. **There is NO fallback**: a declaration is `command` OR `http`, never both. 🛑 Never repeat "no connection ⇒ we fall back to spawn" — an inference, and false.
🛑 **ONE SOCKET OR TEN, THE INVOCATION TABLES ARE THE DAEMON'S — NEVER THE SOCKET'S.** `main` builds `frameSequencerState`, `deliveryNoticeState` and `carryoverState` ONCE and hands them to EVERY `createServer` of the port lane. 🔴 Omitting them made the builder DEFAULT-CREATE one per socket, and `frame-sequencer-pure` then counted arrivals in N maps instead of one: MEASURED on the real daemon, 17 chunks over 32 frames at 4 sockets, chunks 1..8 were delivered FOUR TIMES EACH and chunks 9..17 NEVER. The duplication was visible; the loss was not. ⚠️ **SI tu ouvres une socket de plus, tu DOIS lui passer les trois tables** — `shared-sequencer-gate` rougit sinon, et la voie du rendez-vous est la SEULE exemption, declaree avec sa raison (la voie `command` garde son decoupage par URL).
🔑 **THE CORPUS IS RESIDENT HERE AND NOWHERE ELSE.** `corpus.enableCache(fs.watch)` is called ONLY by this shell, so every spawned hook, lint and test still walks the disk and the differentials see nothing. Invalidation is the KERNEL event on the corpus DIRECTORIES — never a TTL, an mtime or a hash.
🛑 **THE LOSS CLASS IS CLOSED BY ADDRESS, NOT BY COUNT — and the burst is UNCHANGED.** N chunks ⇒ N declarations ⇒ N simultaneous connections. What changed on 2026-09-03 is that the kernel retransmits a SYN again, because the destination left the `uv__is_loopback()` domain. ⚠️ `carryover-pure.js` does NOT make lost frames arrive — it makes the CONTENT come back at the next action. **Never sell it as "nothing is lost any more".**
🛑 **WHAT MAY NOT REOPEN THE LOSS INVESTIGATION**: red `ECONNREFUSED` lines on screen · a burst that feels worse than usual · a new idea about retries, pipes, backlog sizes or timeouts. **The red line is not the observable, the RATE is** — the honest regime is a ~0.5 % stationary floor. ✅ **The ONE fact that reopens it**: lost ÷ POSTs per hour CLIMBS and does not come back. Compute it FIRST. 📌 One exit stays available and it is a CHOICE, not a fix: the `command` lane removes the class by construction, at ~330 ms per declaration — a reversible config decision that belongs to the operator.
🔒 **AND `read ECONNRESET` IS CLOSED, SEPARATELY (2026-09-24): the project is NOT responsible.** From 2026-09-23 the harness read resets on ~1.44 % of POSTs; kernel traces show Windows (`pid=0`) aborting the connection on a retransmission timeout, both ends getting the RST, the daemon idle and waiting (`socket-cut`). A server cannot retry what it never received — the missing retry is the client's (anthropics/claude-code#96657). 🛑 **IF you touch this daemon because of resets, you MUST NOT reopen this — FINAL, NOTHING REOPENS IT: the KM-TEST adapter is the only viable choice (127.0.0.1 measured worse — refusals without SYN retry; a named pipe is impossible for HTTP hooks; the `command` lane was rejected by the operator), so no measurement could lead to an action on our side** (`adapter-windows.md`).
