# http-server.js — the SAME gate, served over a socket. NOT WIRED (2026-08-20).
🛑 **INERT ON PURPOSE.** No `settings.json` entry points here; nothing spawns it. Switching over is the maintainer's explicit decision, taken when no agent is running. Until then its only job is to be PROVEN identical to the spawn lane.
📐 **MEASURED FACTS, 2026-08-20 — do NOT re-research this.** Claude Code **2.1.237**: `type:"http"` is real, verified IN the installed binary (literals `"HTTP hook type"`, `url` = *"URL to POST the hook input JSON to"*, plus `if`/`timeout`/`headers`); five handler types exist (`command`·`http`·`mcp_tool`·`prompt`·`agent`); *"All matching hooks run in parallel"*; output cap **10,000 c per OUTPUT**. Codex **0.146.0**: *"Only `type:"command"` handlers run today"* — `prompt`/`agent` parsed and skipped, **no http**. Sources: `code.claude.com/docs/en/hooks`, `learn.chatgpt.com/docs/hooks`.
🛑 **THE CAP IS PER OUTPUT, NOT PER PROCESS ⇒ N DECLARATIONS ARE STILL REQUIRED.** HTTP changes their PRICE (~330 ms of node startup each → one local POST), never their NUMBER. Collapsing to one declaration would drop an action's capacity to a single frame and make the agent act on partial knowledge.
🛑 **KEEP `lock.js`.** "One daemon, therefore no lock" is the trap: Codex keeps spawning real processes against the same state files, and other sessions exist.
🔴 **AND THE TRAP WAS SPRUNG ON THREE ROUTES — `/emit`, `/turn`, THEN `/purge`, ALL CLOSED 2026-08-23.** The first two wrote the durable class with NO lock, justified as *"one thread, one connection at a time: nothing to serialise against"*. True of the daemon's OWN callers, false against a spawned peer — and since 2026-08-22 the write-through puts both on the SAME files. **209 lost read-modify-writes out of 800 on one `remainder-` key; control with both writers locked, 0-1 of 800.** Nothing corrupt (tmp + rename), but a RECORDED DELIVERY gone, i.e. a document delivered twice, in silence. 🔴 **AND `/purge` WAS THE ONE LEFT BEHIND, found the same day by TLC** (`specs/tla/State.tla`, run `StatePurgeWindow`): it destroys the durable class through the write-through, so a peer whose snapshot PREDATES it republishes that snapshot and a `doc-seen-` record comes back from the dead — the document it names is then WITHHELD for the rest of the session. All three take the REAL lock now, at the SAME address, asked for by `store-resolve.lockDirForKey` (a lock only serialises writers sharing a NAME, and a route may not compose one). ⚠️ The local alias `withLock` is kept on purpose: the gate cannot see `lockModule.withLock(…)`. 🛑 The synchronous rule above is what makes this safe — **at most ONE lock held at a time, never nested**: `/purge` spans BOTH addresses and therefore runs its two sections one after the other.
🛑 **THIS PATH MUST STAY SYNCHRONOUS.** `lock.js` busy-waits and assumed every caller was a short-lived process. Here N frames land in ONE process: an async core would let request A hold the lock while B spins on it for the full timeout — a self-deadlock that looks like a slow daemon, not a bug.
🛑 **NO `deadline.arm()` here** — deliberate inversion of the rule every other shell follows. The deadline kills zombie hook PROCESSES; a daemon is supposed to outlive its request. The bound belongs to the harness `timeout`.
⚠️ **Loopback only, and the dialect is NOT reimplemented**: the response JSON comes from `doc-inject.output()`, the very function the spawn lane uses — a second copy would be a twin that drifts.
🛑 **A DAEMON HOLDS ITS CODE IN MEMORY — the defect a spawned hook CANNOT have.** After a `git pull` it looks perfectly healthy and serves yesterday's logic: a GREEN THAT LIES, the exact thing this repo fears most. Guard = `watchOwnCode`: the kernel TELLS us a file changed (inotify · ReadDirectoryChangesW · FSEvents), we exit, the OS restarts. Zero polling, zero hashing, zero "am I still current?".
🛑 **WE WATCH DIRECTORIES, NOT FILES, AND IT IS MEASURED.** Git renames over the target instead of writing in place, so a file watch follows the dead inode and goes SILENTLY deaf — worse than no watch. `http-daemon-lifecycle.test.js` ② performs that exact rename on the real kernel. The watched set is DERIVED from `require.cache` (a file added tomorrow watches itself), `node_modules` excluded.
🛑 **EXIT CODE NON-ZERO (`90`), for portability not style**: a supervisor only restarts on FAILURE (launchd `KeepAlive`/`SuccessfulExit=false`, and `Restart=on-failure` until socket activation replaced it on Linux). `exit 0` reads as "job done". 🔴 **It was 75 for one hour and 75 was a TRAP**: that is `TEMPFAIL`, and systemd's OWN manual, Example 1, declares *"Exit status 75 (TEMPFAIL), 250 … are considered clean service terminations"* — copying a manual's example, the most normal gesture there is, would have silently turned the stale-code restart into "job done". 90 sits outside every alias and outside that example, so the copy-paste cannot reach it: impossible by construction, not discouraged by a warning. ⚠️ Windows restarts on neither — see `service-units.md`.
📐 **MEASURED 2026-08-20 on the real corpus — and it moves the target.** Round trip **41.49 ms**, engine alone **41.32 ms** ⇒ **the transport costs 0.17 ms**. The 41 ms are the corpus re-read, which the spawn lane pays too (hidden inside node's startup). ⇒ the daemon alone takes an action from ~5.3 s to ~660 ms (16 frames served one after another); the REST of the win needs an in-memory corpus, invalidated by the same watch — a decision, not a detail, and the differential must stay byte-identical.
📐 **NO LEAK, PROVEN BY THE SLOPE, NEVER BY A CEILING.** Ten equal batches, bytes retained per request: **370 → 281 → 181 → 150 → 134 → −1 → 18 → 65 → 50 → −12** — it converges to zero, and the state on disk stays at **0 KB**. A ceiling answers "is it big on THIS machine today"; only the slope answers "does it keep growing", the only question for a process running for months. The gate carries its own SEEN RED: the identical criterion must REJECT a server retaining one object per request.
🛑 **AND THE FIRST VERSION OF THAT GATE WAS A CLIFF — red CI, 2026-08-20.** It compared batch 4 to batch 1 with `< half`; a loaded Windows runner read 361 → 229 → 180 → 184 KB, converging exactly as expected and rejected by four kilobytes. ⇒ **six batches, not four** (the marginal is still 150 B/req at batch 4 and only settles from batch 5), and **averages of head vs tail**, never single readings. A gate that reddens on scheduling noise is a gate people stop reading, then disarm.
🛑 **A LEAK IS NEVER PROVEN ABSENT BY A TEST — the suite is a FLOOR.** It runs thousands of requests in seconds and only catches what retains on the HAPPY path; the vicious ones retain a few bytes on a RARE event and surface after weeks of uptime, which no run reaches. The real assurance is the STRUCTURAL audit at the top of `http-server.js` (the seven known classes of accumulation, each checked by reading) — inherit it, do not redo it.
🔴 **AND THAT AUDIT PRODUCED TWO FALSE ALARMS, KEPT AS A WARNING (2026-08-20).** Reading concluded "an aborted request leaves a pending promise" and "writing to a closed socket kills the process". **Measurement on Node 22.15.1/Windows refuted BOTH**: without any guard the server survived and every request settled. The guards stay — they make the invariant independent of an undocumented runtime behavior, on a process meant to run for months across upgrades — but **never describe them as fixes for an observed defect**. Reading finds candidates; only measurement promotes one to a fact.
⚠️ **NOTHING HERE INFERS LIVENESS.** No health probe, no heartbeat, no timeout used as a verdict. A dead socket answers `ECONNREFUSED` instantly; the service's death is an OS EVENT. 🛑 The hook must NEVER start the daemon: that is how orphans are born, and it is the OS's job.
✅ **MEASURED AGAINST A REAL CLAUDE CODE, 2026-08-20 — the lane DELIVERS, and the last guess is LIFTED.** An `additionalContext` carrying a unique token came back WORD FOR WORD out of the agent. The POST body is IDENTICAL to the stdin payload (`session_id`·`transcript_path`·`cwd`·`prompt_id`·`permission_mode`·`hook_event_name`·`tool_name`·`tool_input`·`tool_use_id`), and **the query string is preserved** — so the frame coordinates travel. An EMPTY answer is harmless: the tool runs, no error. `{}` and empty both work.
🔑 **HOW TO RE-MEASURE WITHOUT TOUCHING ANYTHING**: project hooks are MERGED with the user's (official settings doc). A throwaway directory with its own `.claude/settings.json` declaring one `http` hook, then `claude -p` run INSIDE it — the hook ADDS itself, the operator's config is untouched, other agents see nothing, no quiet window needed.
✅ **SOCKET ACTIVATION SHIPPED 2026-08-20 — the stale-code exit no longer costs an outage.** `watchOwnCode` makes the daemon exit while an agent EDITS this repo, and each window silently cost every other agent its injection; a long enough burst hit the start limit and killed the lane for the fleet. Now the OS owns the listening socket: connections QUEUE in the kernel backlog while no instance runs, and the next one starts a fresh instance — no restart loop to rate-limit, stale code impossible by construction. `Restart=on-failure` is therefore GONE from the systemd unit (`Restart=no`): re-adding it re-arms the burst.
📐 **THE PROTOCOL IS READ, NEVER SNIFFED** — sd_listen_fds(3), systemd 261~rc1, page 2026-05-24: `SD_LISTEN_FDS_START 3`, and it "checks whether the $LISTEN_PID environment variable equals the daemon PID. If not, it returns immediately". 🛑 **That pid comparison is load-bearing**: these variables are INHERITED, so without it a daemon whose parent was activated would listen on a descriptor nobody gave it — silently. Nothing else is examined, no probe, no "does fd 3 look like a socket"; absent the variables the port path runs BYTE-IDENTICALLY to before.
🛑 **`Accept=no` OR THE LANE LOSES ITS REASON TO EXIST** — systemd.socket(5): `Accept=yes` spawns "a service instance for each incoming connection", i.e. one node startup per frame, the ~330 ms this lane deletes, paid again with a supervisor on top. It is also what now guarantees a single instance ("only one service unit is spawned for all connections") where `EADDRINUSE` did.
🔴 **LINUX ONLY, and the other two are DECLARED, never simulated.** macOS has the capability (`Sockets` in the plist) but retrieval goes through `launch_activate_socket`, a C function of the XPC framework — **MEASURED 2026-08-20 on Node 22.15.1: the 54 builtin modules expose NOTHING matching `/launch|activate_socket|listen_fds/`**, so it is unreachable in pure JS and a native addon is refused. Windows has no equivalent, and Node settles it anyway: *"Listening on a file descriptor is not supported on Windows"* (net, v22). Both keep the eager restart AND the silent window.
🔴 **THE "PORT-HOLDING PARENT" IS REFUSED ON WINDOWS — MEASURED 2026-08-20, after THREE agents stalled on it.** The idea (a tiny parent holds the listening socket, a child does the work, the child may exit freely) is exactly what socket activation already gives on Linux. On Windows, in order: ① passing an ACCEPTED SOCKET throws **EMFILE** on the first call — capability absent, not slow; ② `cluster`, the platform's own answer, does not cover it (default `SCHED_NONE` puts the LISTENING socket in the worker ⇒ `ECONNREFUSED` when it dies; forcing `SCHED_RR` moves listen to the primary but it dispatches instead of queuing ⇒ `ECONNRESET`); ③ passing the LISTENING SERVER works — twice over — and the parent DOES keep the port, but a connection issued while no child accepts is **NEVER RESOLVED**: not refused, not reset, it hangs. 🛑 So the parent does not remove the window, it makes it WORSE: today the caller gets an instant, loud `ECONNREFUSED`; with the parent it would wait on a socket nobody answers, up to the harness timeout, PER FRAME. **A fast noisy failure beats a silent hang.** Sealed by cell ⑥ of `http-daemon-lifecycle.test.js` (win32 only, with anti-vacuity) — a DRIFT-TEST on a third party: if it ever turns RED, Windows gained the capability and the parent becomes buildable. Do NOT re-research this from scratch.
🛑 **AND RECYCLING ON AN EXACT COUNT FOLLOWS IT — dropped, not postponed.** It only ever existed to BOUND a leak (`max_leak = leak/request × N`). Two measurements killed the need: the EXACT COUNTS cell (⑤) reads listeners, active handles and module-cache entries after 1 request and after 501 and finds them **EQUAL — zero accumulation, integers, no threshold**; and on Windows each recycle would reopen the hang above. On Linux socket activation makes an exit free, so recycling costs nothing there — but a cure with no measured disease is not shipped. Reopen only if a count above ever moves.
📐 **EXACT COUNTS BEAT THE SLOPE, AND BOTH ARE KEPT.** The slope (③) weighs BYTES — the collector, the allocator and a neighbour process all have a vote, so it answers "does it look like it converges?". Cell ⑤ counts INTEGERS that must be EQUAL, seen RED at exactly 1.000 listener per request. ⚠️ Its client uses a dedicated agent capped at ONE socket: with Node 19+ keep-alive defaults the handle count otherwise depends on timing (measured 2 then 3 on a run where nothing leaked). An exact count must not rest on a default.
🔴 **NO DAEMON = TOTAL SILENCE, MEASURED.** With nothing listening, the tool runs normally, no error surfaces, the agent never learns it acted without its knowledge. **There is NO fallback**: a hook declaration is `command` OR `http`, never both (that would double-inject). 🛑 Never repeat "no connection ⇒ we fall back to spawn" — that was an inference, and it is false. Making this absence OBSERVABLE without any liveness probe is an OPEN item (backlog 60 ②).
✅ **THE DAEMON LISTENS ON BOTH TRANSPORTS SINCE 2026-08-21 — and before that the kernel lane had no other end.** It bound ONLY the TCP port while `state-client.js` connects on `endpoint()`: **nobody was listening where the client knocks**, so switching the shells over would have sent every frame to `ENOENT`, hence to the local state-less path, hence `once` withheld on EVERY action. 🛑 **The three-OS proof could not see it**: `state-daemon.test.js` forks its OWN test daemon (address in `argv[2]`), never `http-server.js` — it proves the MECHANISM. **A green on a twin is not a green on the thing**, and that is the lesson to carry, not the fix.
⚠️ **BOTH ADDRESSES ARE LEGITIMATE, neither is a mistake**: the PORT serves Claude Code's native `type:"http"` handler (it takes a URL, and a pipe is not a URL) · the RENDEZVOUS serves the client lane — spawned hooks, and Codex which has no `http` handler at all. **One handler, two transports**; a second protocol would drift from the first. ⚠️ **ONE `store` for both**, deliberately: two would be the "two memories" defect `client-lane.md` forbids, reintroduced from inside the daemon.
⚠️ `kernel-bind` takes the second address, never a bare `listen`: on macOS a killed daemon leaves its socket FILE, and the entry is cleared only after ASKING the kernel who answers. Proof = `test/dual-transport.test.js` (same server, byte-for-byte equality, anti-vacuity floor, seen RED with a single listener).
🔑 **THE CORPUS IS RESIDENT SINCE 2026-08-21 — where the 41 ms live.** `corpus.enableCache(fs.watch)` is called ONLY by the daemon shell: every spawned hook, lint and test still walks the disk byte for byte, so the differentials see nothing. Invalidation is the KERNEL event on the corpus DIRECTORIES — a doc moving DROPS the snapshot and NEVER exits (only CODE moving justifies the exit); no timer, no TTL, no mtime. A root whose watch cannot be armed is not kept: we re-read every time rather than serve what we cannot be told about. Ceiling = 8 roots × one corpus ⇒ a few MB, flat under uptime and traffic.
