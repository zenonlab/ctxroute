# http-daemon-lifecycle.test.js — the daemon lives for weeks, or it does not ship

🛑 **A DAEMON HOLDS ITS CODE IN MEMORY — the defect a spawned hook CANNOT have.** After a `git pull` it looks perfectly healthy and serves yesterday's logic: a GREEN THAT LIES. 🔴 The guard was an INFERENCE until 2026-08-24 (*"the kernel tells us a file changed"*): on the FROZEN copy, which nothing had written to, the daemon still killed itself **258 times**, and the killing event carried `mtime` and `ctime` UNCHANGED with **only `atime` moving**. Merely READING a file killed the service. ✅ Freshness is now an OBSERVATION at the point of use — bytes COMPILED against bytes on disk. Full account: `stale-code.md`.
🛑 **WE WATCH DIRECTORIES, NEVER FILES, AND CELL ② PROVES IT ON THE REAL KERNEL.** Git renames over its target, so a file watch follows the dead inode and goes SILENTLY deaf — worse than no watch. The watched set is DERIVED from `require.cache`, `node_modules` excluded. ⚠️ The watch is an OPTIMISATION since 2026-08-24, no longer the guarantee.
🛑 **`corpus.enableCache` USES THE SAME WATCH AND MUST NOT BE HARMONISED WITH IT** — a spurious invalidation there costs one re-read, where a spurious exit cost the fleet its injection window. They answer opposite questions on purpose.
📐 **NO LEAK IS PROVEN BY THE SLOPE, NEVER BY A CEILING.** Ten equal batches, bytes retained per request: 370 → 281 → 181 → 150 → 134 → −1 → 18 → 65 → 50 → −12, converging to zero. A ceiling answers "is it big today"; only the slope answers "does it keep growing", the only question for a process running for months. 🛑 The first version of that gate was a CLIFF (red CI 2026-08-20): it compared batch 4 to batch 1, and a loaded runner converging exactly as expected was rejected by four kilobytes. ⇒ **six batches, and AVERAGES of head vs tail**, never single readings — a gate that reddens on scheduling noise gets disarmed.
🛑 **A LEAK IS NEVER PROVEN ABSENT BY A TEST — this suite is a FLOOR.** It catches what retains on the HAPPY path; the vicious ones retain a few bytes on a RARE event and surface after weeks. The real assurance is the STRUCTURAL audit at the top of `http-server.js` — inherit it, never redo it. 🔴 That audit produced TWO FALSE ALARMS, kept as a warning: "an aborted request leaves a pending promise" and "writing to a closed socket kills the process" were both REFUTED by measurement. The guards stay, but **never describe them as fixes for an observed defect** — reading finds candidates, only measurement promotes one.
📐 **EXACT COUNTS BEAT THE SLOPE, AND BOTH ARE KEPT.** The slope weighs BYTES, where the collector and a neighbour process both have a vote. Cell ⑤ counts INTEGERS that must be EQUAL after 1 request and after 501 — listeners, active handles, module-cache entries — seen RED at exactly 1.000 listener per request. ⚠️ Its client uses an agent capped at ONE socket: with Node 19+ keep-alive defaults the handle count otherwise depends on timing. **An exact count must not rest on a default.**
🔴 **THE "PORT-HOLDING PARENT" IS REFUSED ON WINDOWS — MEASURED, after THREE agents stalled on it.** ① passing an ACCEPTED SOCKET throws `EMFILE` on the first call ② `cluster` does not cover it (`SCHED_NONE` puts the listening socket in the worker ⇒ `ECONNREFUSED` on its death; `SCHED_RR` dispatches instead of queuing ⇒ `ECONNRESET`) ③ passing the LISTENING SERVER works and the parent does keep the port, but a connection issued while no child accepts is **NEVER RESOLVED** — not refused, not reset, it hangs. 🛑 So the parent makes the window WORSE: a fast noisy failure beats a silent hang. Cell ⑥ is win32-only with anti-vacuity, and it is a **DRIFT-TEST on a third party**: if it ever turns RED, Windows gained the capability. Do NOT re-research this.
🛑 **RECYCLING ON AN EXACT COUNT IS DROPPED, NOT POSTPONED.** It existed only to BOUND a leak; cell ⑤ finds zero accumulation, and on Windows each recycle reopens the hang above. **A cure with no measured disease is not shipped.** Reopen only if a count moves.
