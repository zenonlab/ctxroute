# lifecycle — WHEN THE DAEMON RUNS, AND WHO STARTS IT (2026-09-29)

🔑 **ONE PRODUCT, ONE SETTING, DEFAULTS THAT DEPEND ON WHERE IT RUNS** — `http.lifecycle`: `auto` (default) · `on-demand` · `login`, plus `http.idleSeconds` (default 1800). `auto` resolves on what a RESTART depends on: Linux and macOS ⇒ `on-demand` (the OS holds the socket, the next connection starts a fresh daemon); EVERY Windows edition ⇒ `login`. 🔴 **Windows desktops were `on-demand` for one evening and a live proof refuted it (2026-09-30)**: with a security suite pausing Task Scheduler, a daemon that left on idle could not be restarted — the scheduler answered "the task is disabled". A running daemon survives a disabled task; an idle one cannot come back. `on-demand` stays an explicit Windows opt-in, never the default — cell ④ of `lifecycle-pure.test.js` keeps it that way. Every tool shipped to both servers and consumers (Ollama, Tailscale, PostgreSQL) does this — never two editions.
📐 **IDLE COSTS NO CPU, IT COSTS MEMORY** — measured 2026-09-29: an idle Node HTTP server burns 0 ms of CPU over 15 s, with or without the event-loop histogram; the production daemon held ~300 MB with 4 threads. `on-demand` exists to give that memory back on a consumer machine, never to "save compute".
🛑 **THE STOP IS BY INACTIVITY, NEVER BY COUNTING SESSIONS.** Counting is coordination between PEERS: a session that crashes never says goodbye, so the count lies for ever — a daemon nobody stops, or one killed under a live session. The window closes on EQUALITY of ONE shared counter (`Int32Array` over a `SharedArrayBuffer`, bumped by every request of every thread and lane), so the daemon leaves between one and two windows after its last request. 🛑 **SI you add a server, a lane or a thread, you MUST hand it `activity`** — a server that does not count lets the main thread see silence and leave while that server serves (`daemon-idle-exit.test.js` ① is red when the count is removed).
🛑 **IDLE EXIT IS `exit 0`, AND THAT IS WHAT MAKES IT SAFE EVERYWHERE**: supervisors restart on FAILURE only — the Windows task's EventTrigger fires on a non-zero result, systemd has `Restart=no`, launchd has no `KeepAlive`. It shares `leaveCleanly` with the signal stop (flush, drain the owner, journal, exit). ⚠️ The journal line is written by a THUNK carrying the event name LITERALLY: `lifecycle-log.test.js` proves every event is emitted by reading `lifecycle.record('<name>'`, and a name passed as a variable blinds it.
🛑 **THE START IS ASKED OF THE OS SUPERVISOR, NEVER DONE BY A HOOK.** `daemon-ensure.js` (SessionStart + UserPromptSubmit) asks Task Scheduler to RUN the task — a no-op while it runs (`IgnoreNew`, ~60 ms measured), a start when it does not. A hook spawning `node` would be an orphan the harness can kill, with nobody to supervise the exit-90 restart. On Linux/macOS the unit holds the socket and the first connection starts the daemon: `ensureCommand` answers `null`, by design.
⚠️ **THE HOOK NEVER PRINTS PLAIN TEXT AND NEVER READS STDIN**: on both events plain stdout BECOMES CONTEXT. Its ONE admissible output is a `{systemMessage}` JSON line (shown to the USER, injects nothing), and only when THREE facts hold (`ensureNotice`): the request FAILED, the scheduler's XML says the task is DISABLED, and the KERNEL REFUSES a connection to the daemon. 🔴 **The first version spoke on a disabled task alone and a live proof caught it lying (2026-09-30)**: a disabled task does not stop a running daemon, and a security suite disables it at every screenshot. 🛑 **IF you change the condition, you MUST keep the KERNEL's answer** — never infer "dead" from anything else. ⚠️ The probe bound (`PROBE_BOUND_MS`, 5 s) sits above the MEASURED refusal time on the Windows adapter (2,042 ms — the kernel retransmits the SYN before refusing); 2 s turned every real outage into silence, and a cell holds the floor. A healthy prompt pays ONE request; the query and the probe run only on failure. Fail-open, exit 0 always; `deadline.arm()` lives INSIDE `require.main`.
🔴 **IT ALSO CLOSES A MEASURED OUTAGE IN `login` MODE**: on 2026-09-29 a security suite's "do not disturb" mode (Avast, rule `PauseSystemBackgroundTasks`, triggered by any full-screen app) disabled the task at logon; the daemon never started while every check stayed green. Asking at every prompt turns "never came up" into "came up at the next prompt", and `doctor --settings` now reads the task's `<Settings><Enabled>` (language-neutral XML — the table format is LOCALISED) and screams when it is `false`.
⚠️ **NO TASK IS `unmeasured`, NEVER `disarmed`**: a CI runner or an adopter supervising otherwise has none, and the scheduler's refusal is localised text. Linux/macOS supervisors have no probe yet — SAID as `unmeasured`, never counted healthy.
⚠️ **`install-windows.ps1` RESOLVES THE MODE WITH THE SAME CODE** (`paths.httpLifecycle` + `resolveMode` via `node -p`): `on-demand` drops the `<LogonTrigger>`, `login` keeps it; the exit-code EventTrigger stays in both. A refused declaration stops the install. The task name lives in `WINDOWS_TASK_NAME`, held equal to the installer's `$TaskName` by a drift cell.
🛑 **A REFUSED `lifecycle`/`idleSeconds` STOPS THE DAEMON'S START** (`lane-degraded fatal code=LIFECYCLE_REFUSED`), before any socket — never a quiet `auto`. The resolved mode and its reason ride the `start` journal line (`lifecycle`, `lifecycleReason`, `idleSeconds`).
