# service/ — the OS units of the HTTP lane. NOTHING IS INSTALLED (2026-08-20).
⚠️ **Linux AND macOS are socket-activated; only Windows keeps the eager model.** Read that asymmetry before touching any unit: on the two activated OSes the SUPERVISOR binds, so the address lives in the unit and the daemon's own port setting is ignored.
🛑 Never add a health check, heartbeat, PID file or "is it already running?" probe: the OS supervises, and the KERNEL refuses a duplicate with `EADDRINUSE` — under socket activation that refusal MOVES to systemd (`Accept=no` ⇒ "only one service unit is spawned for all connections"), it never becomes ours. The only admissible delay is the alive-but-wedged one, and it says so where it is written.
✅ **LINUX IS SOCKET-ACTIVATED SINCE 2026-08-20 — `ctxroute-http.socket` is what you enable, NEVER the `.service`** (which has no `[Install]` left). systemd holds the listening socket, so a stale-code exit costs no outage: connections QUEUE in the backlog and the next one starts a fresh instance. ⇒ `Restart=no` in the service: **re-adding `Restart=on-failure` re-arms the burst** it was removed for.
🛑 Three lines in the socket unit are load-bearing: `Accept=no` (`yes` = one node process PER CONNECTION = the cost the lane deletes), `ListenStream=127.0.0.1:` (no auth exists, the socket IS the boundary), and the ABSENCE of `FlushPending=` (it "clears the socket's buffers after the triggered service exited" — those queued connections ARE the repair). The two burst limits (`StartLimitBurst` on the service, `TriggerLimitBurst` on the socket) are sized in ACTIONS, 16 frames each; hitting the socket's puts it "into a failure mode … not connectible anymore until restarted".
✅ **macOS IS SOCKET-ACTIVATED TOO SINCE 2026-08-23 — via a COMPILED SHIM, and the plist lost `RunAtLoad` + `KeepAlive` in the same gesture** (re-adding either re-arms the burst, exactly like `Restart=on-failure` on Linux). launchd's `Sockets` needs `launch_activate_socket`, a C function (measured 2026-08-20 — the 54 Node builtins expose nothing matching `/launch|activate_socket|listen_fds/`); `service/launchd-socket-shim.c` is that translation and is NOT an addon — it `dup2`s the descriptor to 3, publishes `LISTEN_FDS`/`LISTEN_PID`, then `execv`s node (same pid, so launchd still supervises ONE process) and the daemon reads the protocol it already implements for systemd. **ZERO engine lines.**
🛑 **The pid the shim publishes MUST be its own** — sd_listen_fds(3): the daemon "checks whether the $LISTEN_PID environment variable equals the daemon PID. If not, it returns immediately", because these variables are INHERITED. Publish a parent's and node listens on a descriptor nobody gave it, SILENTLY. That exact line is what the CI sabotages (a COPY in the tmpdir, never in place — no sabotage switch may exist in the tracked source) and the macOS job is REQUIRED to go red.
🛑 **`Listeners` is ONE name shared by the plist and the shim's first argument**; renaming one side makes every activation fail with "no such socket". The port lives ONLY in `SockServiceName` — `EnvironmentVariables` was REMOVED, not left as a second copy the daemon ignores while activated.
🔴 Windows still CANNOT, and the gap stays DECLARED: no equivalent, and Node refuses anyway ("Listening on a file descriptor is not supported on Windows"). It keeps the eager restart and the silent window with it.
🔴 **THE EXIT CODE IS 90, AND 75 IS THE TRAP IT AVOIDS.** 75 is `EX_TEMPFAIL`, which systemd ALIASES and puts in its own manual as Example 1 — *"Exit status 75 (TEMPFAIL), 250 … are considered clean service terminations"* (systemd 261~rc1, page 2026-05-24). Copying a manual's example is the NORMAL gesture; with 75 it silently turned our restart into "job done". 90 is outside every alias and that example ⇒ impossible by construction, not discouraged.
🛑 Never re-type the number: `test/service-units-gate.test.js` DERIVES it from `EXIT_STALE_CODE` (`src/hooks/http-server.js`), forbids an active `SuccessExitStatus=` in the unit, and reddens on any stale literal here or in `service/`. A retired code stays writable ONLY in the manual's own wording (`Exit status N`) — asserting it of our daemon (`exits N`) is RED, the hole that let the first version certify a drift.
📐 Exit 90 brings the daemon back on Linux AND macOS via the SOCKET, never a restart: the next CONNECTION starts a fresh instance and the ones arriving meanwhile queue in the backlog. ⚠️ Expect the macOS respawn throttle to delay that first answer — ANSWERED is the whole difference from refused. ⚠️ On Linux what can still refuse a start is the start LIMIT, not the `failed` state (systemctl(1): `reset-failed` is needed only when "a unit's start limit … is hit").
🔴 On Windows it does NOT: [MS-TSCH] 2024-04-23 restarts only when a start condition fails or an action FAILS TO START — a task that ran and exited is a task that COMPLETED. The exit-code restart is the `EventTrigger` on Operational event 201, and that XPath is UNVERIFIED without installing.
