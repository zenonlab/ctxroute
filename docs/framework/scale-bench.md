# scale-bench.test.js: the SLOPE at the real sizing, never a millisecond
🛑 **ASSERT ON RATIOS ONLY.** A duration belongs to this machine; how the cost GROWS when the load multiplies belongs to the algorithm. Never add a threshold in ms, in bytes or in requests per second.
🔴 **TWO AXES, AND THEY ANSWER DIFFERENT QUESTIONS — never quote one for the other.** **A = HELD STATE** (cells ①②, scopes 128→1024): does holding more agents' memory cost more per request? **B = CONNECTED AT ONCE** (cells ③④, 64→1024 established clients, held state FROZEN at 128 scopes): does serving ONE agent cost more because N others exist? **A map with 1024 entries is not 1024 concurrent clients** — until 2026-08-21 only A existed, and work item I asks B.
🔴 **MARGIN A = 1.67, DERIVED FROM THE MEASURED PAIR** HEALTHY 0.89 · SABOTAGED 3.13 ⇒ √(0.89×3.13). It was 3.0 and the sabotaged store cleared it by 4 % — the gate CERTIFIED a defect.
📐 **BAR B = √(load factor) = √8 = 2.83, `Math.sqrt` OF THE LEVELS, never a literal** — geometric mean of model O(1) (ratio 1) and model linear-in-fleet (ratio 8 = 768/96). Move a level, the bar moves. **~1.0 = healthy · ≥ 8 = linear in the fleet · ≥ 2.83 reddens.**
📐 **MEASURED 2026-08-21, busy workstation, at the FIRST range 64…512 (K=4, bar 2.00): healthy 0.81 / 1.29 · sabotaged 2.95 / 2.55 · jitter 1.71 / 3.35.** Cell ④ reddened as it must, but 2.55 vs 2.00 is only 27 % of clearance. Fitting `C + a·N` on those two runs gives a fixed cost worth **52–90 connections' worth of walking** — and a fixed cost is diluted by a LARGER N, never by a different threshold. So the RANGE was widened (predicted 4.6–5.6 vs 2.83 — a prediction, not a reading). 🛑 The bar was NOT lowered and the sabotage was NOT made louder: tuning a strawman until it clears gives a gate that only catches the defect it was shaped for.
🛑 **THE SUB-BATCH IS SIZED IN TIME, NOT IN CALLS — and the noise figure that GATES is the INTER-QUARTILE ratio, not max/min.** At 160 calls a batch lasted under 1 ms against a ~15.6 ms scheduler quantum, so one preemption WAS the reading and the refusal flipped 1.71 → 3.35 between identical runs. Now: 9 sub-batches, each calibrated at runtime (min of 3 pilot passes — a preemption only ADDS time) to last ≥ 20 ms; `nu` = the spread of the CENTRAL half (the noise of the median, the statistic actually used), `spread` = max/min, reported and gating NOTHING. Cell ③ also asserts the batch really reached the floor. **This also BOUNDS the bench's wall cost**: heavier work makes batches shorter, never runs longer.
🛑 **THE REFUSAL NAMES A SATURATED MACHINE, not background activity** — that is the design intent of the two fixes above, to be confirmed by the next run, never asserted as measured. `nu ≥ BAR` ⇒ loud "THIS RUN CANNOT DECIDE", never a quiet green, and never a widened bar.
🔴 **CONNECTIONS OPEN IN WAVES OF 64 — a KERNEL fact, measured:** one burst overruns the LISTEN BACKLOG and Windows REFUSES what it cannot queue (64 → 0 refused · 128 → 0 · 256 → 152 · 512 → all 512). Not a bigger backlog (one kernel's number, we ship on three) and not a timer: each wave is drained by the server's own `connection` event. A bench that dies there measures the accept queue and gets read as if it had measured our cost.
🛑 **COST TIMED ON `handle()`, never a round trip** (the socket is a 0.17 ms CONSTANT that buries the quantity). Axis B's in-flight round trips are the REALITY anchor: PRINTED, asserted on by NOTHING — one point has nothing to compare with.
🛑 **ANTI-VACUITY IS LOAD-BEARING, and axis B has two ways to measure nothing:** never open the sockets, or open them client-side while the server never accepts. Hence the SERVER's own `connection` count per level, plus `tenues` and `portees === 128` both read BEFORE the round trips (the anchor opens its own sockets and creates a `doc-seen-` scope: reading after reported 544 vs 512 and accused sockets of dying when none had).
🛑 **EVERY CELL PRINTS ITS READINGS, RATIOS, JITTER AND BATCH SIZES BEFORE ASSERTING**, success included. A gate that only speaks when it fails turns its own threshold into folklore.
⚠️ **`test.sequential` ON ALL FOUR — LOAD-BEARING.** The `integration` lane is `sequence.concurrent`, so by default the four drivers would time themselves while competing: that corrupts the RATIO, not just the noise. **Load imposed: ONE node process at a time, ~2048 loopback fds, tens of MB** — axis B's clients are SOCKETS, never processes.
⚠️ **NO TIMER, EVER**: readiness = the socket's own `connect`/`listening` event and the server's `connection` handler resolving a promise; completion = the child's EXIT; the driver is killed in a `finally` on every path. **HEAVY LANE by content**: no per-test timeout, the global 30 s applies, and it runs on every push.
