# free-port — ONE allocator for every port a suite hands to a daemon (2026-09-23)
🔴 **THE DEFECT, MEASURED**: `stale-code-guard ⑥bis` read exit 1 where 90 was asserted, in the full run only (8/8 green alone). The daemon's journal said `bind-refused lane=port`: the test had taken its port with `listen(0)`, CLOSED the probe, then forked the daemon — and in between the kernel gave that port to a neighbour's outgoing `connect()`. The ephemeral range serves BOTH. Seven suites carried their own copy of that probe.
✅ **CLOSED BY WHERE THE PORT COMES FROM, NEVER BY A RETRY**: `test/support/free-port.js` allocates from 20000-31999, below every vendor default ephemeral floor (Linux 32768, Windows/macOS 49152), so no `connect()` can ever be given one. Each port is still PROBED by a real bind: a port somebody holds is skipped, never guessed free.
🛑 **IF you fork a daemon on a port, you MUST pass `span` = the number of listeners it will open** (`DEFAULT_LISTENERS` when the config declares none): the daemon counts up from its base, and an allocator told `1` hands the NEXT caller a port that daemon is about to bind.
🛑 **`rules/no-released-port-probe.yml` + `test/released-port-probe-gate.test.js` = ZERO tolerance, no budget**: a `close` that hands the number out, inside the `listen(0)` that measured it. A server that listens on 0 and KEEPS serving is legitimate and not matched; neither is a probe closed after a child inherited a DUPLICATE of its descriptor (`http-socket-activation`) — nothing is released there.
⚠️ **The lane classifier reads `support/free-port` as binding an address** (`vitest-projects.mjs`): a suite using the allocator no longer writes `.listen(` and would otherwise leave the daemon lane with the very act that puts it there.
⚠️ **DECLARED RESIDUAL**: two test processes probing the same port of the band at the same instant. Start spread by pid and thread, cursor advances past every port handed out — never observed, and no longer the ephemeral pool.
🔴 **ONE PROCESS DID HAND A PORT OUT TWICE — CLOSED 2026-10-01 (`nextBlock`).** The base was `cursor % (BAND_SIZE - span)`: a modulus that CHANGES WITH THE SPAN, so requests of different sizes mapped one cursor to different places and overlapped (`{20003,4}` then `{20006,3}` on the Linux runner, by pid — hence "flaky"). Now the offset is `cursor % BAND_SIZE` for every span and a block that would cross the end of the band wraps instead. 🛑 **IF you change how a base is computed, it MUST stay independent of `span`** — a cell walks EVERY starting cursor of the band, and keeps the former formula in memory to prove it can see the overlap.
