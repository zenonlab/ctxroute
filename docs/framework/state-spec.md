# specs/tla/State.tla — TLA+ spec of the DURABILITY frontier (2026-08-23)

⚠️ **SCOPE, AND IT IS THE COMPLEMENT OF `Transport.tla`, NEVER AN OVERLAP.** `Transport.tla` proves DELIVERY (leader election, the `remainder-` queue, the split); this module proves DURABILITY: N processes doing a read-modify-write on the SAME durable key, and one question — *once a delivery has been RECORDED, can that record disappear?* The decision core is deterministic and stays out of both.
🛑 **THE ABSTRACTIONS CARRY THE PROOF, so changing any of them means updating `State.tla` and re-running `npm run spec:tlc`**: ① tmp+`rename` makes a write ONE step (nothing is ever corrupt — what is lost is an UPDATE) · ② `plan-` is the ONLY ephemeral prefix, so the durable class is everything else and BOTH lanes write it to the same files · ③ every durable writer takes the lock at `store-resolve.docLockDir`/`turnLockDir` · ④ a purge takes NO lock. Sealed by `state-spec-gate.test.js`, which reads those four facts out of the code.
🛑 **ZERO CLOCK IN THE MODULE, AND THE TWO FORCING KNOBS ARE WHY.** An INFERENCE about death is modelled as pure nondeterminism (`STALE_FORCING` — a held lock may simply be taken); a PROOF of death is modelled as a guard on the owner's liveness (`KERNEL_FORCING` — `~alive[lockOwner]`, which in the code is `process.kill(pid, 0)` answering `ESRCH`). Introducing a timer here would model a THIRD protocol and quietly make every verdict about it. ⚠️ `KERNEL_FORCING` is only FAITHFUL while the code really asks an authority that knows — anchored by `state-spec-gate.test.js`, which holds `lock.js` to that question and to exactly ONE remaining clock comparison (the unidentified-holder residual).
✅ **ANSWER ① — WITH THE LOCK AND WITHOUT STALE FORCING, NOTHING RECORDED IS LOST** (`State.cfg` green, 364 distinct states, depth 12), daemon death, restart and a concurrent compaction all enabled. The death is free because the daemon owns nothing: `Revive` leaves `disk` untouched, which is the write-through of 2026-08-22 written as a formula.
🔴 **ANSWER ② — COMMUTATIVITY IS NOT THE PROPERTY THAT SAVES YOU, AND THE SPEC SAYS SO IN ONE BOOLEAN.** The recorded operation is ALREADY commutative and idempotent (set union) and `StateCommutativeShared` is STILL red: the loss lives in the read-modify-write, when one shared value is replaced from a stale snapshot, not in the order of the operations. What holds for every interleaving with NO lock is `SLOT_PER_WRITER` — each writer replaces only its OWN file, a reader takes the union (`StateCommutativeSlots` green, 1268 states, depth 15). 🛑 That green is worth exactly what `StateSlotsOverlap` proves: two writers really are in the critical section together in that same configuration.
🔴 **`StateLockless` IS THE VALIDATION OF THE WHOLE MODEL, NOT A SABOTAGE** — it is the 2026-08-23 race verbatim (209 lost read-modify-writes out of 800, measured on two real processes). A spec that could not find it would be a comfortable fiction. NEVER make it green.
✅ **`StateStaleForcing` IS ANSWERED (2026-08-23) — it stays RED for ever as a LEGACY negative-check, never as an open finding.** It models the design we LEFT: forcing an "abandoned" lock on a clock lets a second writer in while the first is merely descheduled. `lock.js` now asks the KERNEL instead (`process.kill(pid, 0)`; `ESRCH` = a proof of death), which is `StateKernelForcing` — GREEN on TypeOK · NoLostRecord · AtMostOneInCrit, with `StateForcingFires` requiring `NeverForced` VIOLATED so that green cannot mean "nobody ever forced". Both horns are now held at once: a dead holder's lock IS released, and no record is lost. 🛑 If `StateStaleForcing` ever goes green, `NoLostRecord` has stopped discriminating and the kernel-forcing proof is hollow.
🔴 **ONE FINDING THE CODE HAS NOT ANSWERED, required RED and silent in production**: `StatePurgeWindow` — a compaction takes no lock, so a writer whose snapshot predates it republishes it, and a resurrected `doc-seen-` record WITHHOLDS a document that was owed for the rest of the session. `StateStuckLock` still exhibits the dilemma's other horn — the lock DIRECTORY outliving its holder — which is now RESOLVABLE (the kernel frees it) rather than permanent, except for the two residuals declared in `lock.md`: pid reuse, and a death inside the two-syscall window.
⚠️ **ONE RUNNER, TWO MATRICES**: `run-tlc.mjs --matrix state-runs.json`, module read from the matrix. `npm run spec:tlc` runs BOTH. 🛑 cfg names must stay UNIQUE ACROSS matrices (`.cfg` and `-metadir` are derived from them) — sealed by a cell.
⚠️ **NOT MODELLED, STATED NOT HIDDEN**: which record a writer decides to produce (that is `Transport.tla`'s `AtMostOnceDelivery`), the fail-open lock timeout (it writes nothing, so it can neither lose nor create a record), and LIVENESS.
