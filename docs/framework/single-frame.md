# BANDWIDTH OF ONE ACTION — why N frames, and why NOT a single one
🛑 **JUDGMENT REVERSED IN 24 H, REWRITTEN (07/08/2026).** This doc advocated a SINGLE gate declaration. **It was wrong**, and the return to 12 is done. Reason for the reversal: the requirement was never display order, but that **the context be COMPLETE before the next tool call**. At 1 frame the capacity drops to ~7,661 c ⇒ a 53,830 c skill spreads over 8 actions ⇒ **the agent acts 7 times with partial knowledge**. Disorder is reassembled (`k/N`); knowledge absent at the moment of acting is not.
🔴 **THE MEASUREMENT USED TO JUSTIFY THE REMOVAL WAS BIASED**: "the 12 frames saturated only 1 time out of 74 actions" counted the frames USED. The right observable was the **deferred-doc counter, which no longer came back down to zero** — a `dumb` corpus is re-decided at EVERY action, so undersizing N puts the queue into perpetual rotation (already written in `gate.md`, never linked to the observation).
⚠️ **ORDER IS GUARANTEED BY NO HARNESS, and it is not recoverable** — official doc re-read 06/08/2026: *"All matching hooks run in parallel"*, aggregation order **unspecified**, and the 10,000 c cap applies to the **5 handler types** (`command`/`http`/`mcp_tool`/`prompt`/`agent`). ⇒ guaranteed order ⟺ SINGLE output ⟺ content ≤ one frame. 🛑 NEVER code a precedence chain between processes to force ordering: that would bet on undocumented behavior (forbidden by `budget.md`).
⚠️ **CAPACITY MEASURED 07/08/2026**: 1 frame = **7,661 c** · 12 frames = **91,932 c** · worst real load = **65,265 c (71 %)** of which **53,830 c for the skill alone**. Beyond that nothing is lost (queue) but the agent will have acted before delivery ends.
⚠️ **RAISING N COSTS**: each frame is a process launched at EVERY tool call, **even empty** (~330 ms) — 12 ⇒ ~4 s, 50 ⇒ ~17 s. Unexplored lead to escape it: `http` handlers launch no process, but require a daemon (the framework has none today).
🛑 **THE "DUPLICATE" NEVER EXISTED — FALSE DIAGNOSIS, REFUTED BY MEASUREMENT (07/08/2026).** We thought we saw chunk 7/8 of the skill delivered 2× (seals `2bc5f3df` then `03d7e9f2`) and inferred a race between the N processes over the queue. **FALSE**: the transcript shows a **`PreCompact` hook between the two** (06:24:24). Compaction PURGES the states ⇒ the skill (`once`) becomes deliverable again and is re-injected WHOLE. **That is the DESIGNED behavior** — without it, the agent would restart without its skill after every compaction. Reproduction attempted 07/08 (12 genuinely parallel processes, 2 actions, 105 segments queued): **0 duplicate**, the queue drained cleanly `#12/23` → `#13/23`.
⚠️ **THE LESSON, THOUGH, IS TO KEEP**: two occurrences of the same identifier ARE NOT a duplicate until you have looked at WHAT LIES BETWEEN THE TWO. The missing fact (the compaction) was three lines away in the transcript. An unverified observation hardened into certainty by being copied into the code, the docs and the backlog — and served as the main argument for removing a capability that worked. **Before carving a defect: REPRODUCE it.**
